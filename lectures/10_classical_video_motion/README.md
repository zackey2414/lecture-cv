# 第10回 古典的な動画処理 — フレーム差分・背景差分・オプティカルフロー・meanshift/camshift

## 🎯 この章のゴール

この章を終えたとき、あなたは「動画の中で**何がどう動いたか**」を、機械学習をいっさい使わずに OpenCV だけで抽出・可視化できるようになります。扱うのは古典的動画解析の四本柱——**フレーム差分／背景差分**（動いている前景を抜く）、**Lucas-Kanade 疎オプティカルフロー**（選んだ点を追う）、**Farnebäck 密オプティカルフロー**（全画素の動きを推定して HSV で塗る）、そして **meanshift / camshift**（色ヒストグラムで物体を追う）です。いずれも CPU だけで軽快に動き、ネットもカメラも要りません。しかもサンプル映像は各スクリプトが `numpy`/`cv2` で**合成生成**するので、手元に動画が無くてもすべてを再現できます。

これらはいずれも「学習なし」であるがゆえに、**何を仮定しているか・どこで破綻するか**が数式レベルで透けて見えます。それぞれが置く前提は明快で、背景差分は「背景は静止している」、オプティカルフローは「同じ点の明るさは変わらない（輝度一定）」、meanshift は「対象の色分布は変わらない」と仮定します。本章ではこの前提を意識しながら手を動かし、前提が崩れる場面（背景が動く・照明が変わる・似た色が背景にある）で各手法がどう壊れるかまで体感します。そしてこの経験は、のちに学ぶ**深層フロー RAFT（第27回）**や**多物体追跡 ByteTrack/DeepSORT（第28回）**が「古典の何を肩代わりしているのか」を理解する土台になります。

到達点を一言でいえば、**合成した動く図形の連番フレームに対して、背景差分で前景マスクと外接矩形を出し、疎フローで特徴点の軌跡を描き、密フローを HSV と矢印で可視化して終点誤差(EPE)の概念に触れ、meanshift/camshift で色追跡の窓を動かす——という一連の動き解析を自分の手で書き、それぞれの長所・限界・使い分けを説明できる**ことです。あわせて、フローと色追跡という「動きで追う」「見た目で追う」2 系統の違いも腑に落とします。

## 1. 動画とは静止画の連続 — 本章の合成データ

動画は突き詰めれば**連続した静止画（フレーム）の並び**です。したがって動き解析の正体は「**隣り合うフレームを比べる**」ことに尽きます。前回（第9回）では `cv2.VideoCapture` で動画を 1 枚ずつ読み出す I/O を学びましたが、本章はその先へ進み、読み出した連続フレームから**動き**という情報を取り出します。実データを使わずに学べるよう、本章では共通ヘルパ `cv_helpers.py` の `make_motion_frames()` が、静止した背景の上を 2 つの物体が動く 40 枚のフレーム列を合成します。

合成データには「**答えが分かっている**」という決定的な利点があります。物体の軌道も、背景が静止していることも、平行移動量も、すべてこちらが決めて作っているので、「フローが正しく出たか」「追跡窓が物体に乗っているか」を客観的に確かめられます。そして `make_motion_frames()` が用意する 2 つの動く物体は、このあとの各手法に合わせて性格を変えてあります。

- **テクスチャ付きスプライト**（市松模様＋図形）: 角（コーナー）が多く、`goodFeaturesToTrack` が追跡点を拾いやすい。剛体のまま左→右へ並進し、上下に少し揺れる。**疎/密オプティカルフロー**の主役。
- **緑の円**: 背景と色が大きく違うので**色ヒストグラム追跡**に向く。別の軌道で動き、半径が `14→24px` と徐々に増えるので、**camshift のスケール追従**を見せられる。
- **静止ランドマーク**（背景に置いた小さな模様）: 動かない角を提供し、LK で「動く点は長い軌跡・静止点は軌跡なし」という対照を作る。

このように、1 つのシーンに「動く・静止する・色が違う・テクスチャがある」要素を盛り込むことで、4 つの手法すべてを同じデータで体験できます。加えて、密フローの定量評価のためだけに、`make_translating_pair()` が**既知の平行移動だけで関係づく画像ペア**を別途生成します（真のフローが全画素 `(dx, dy)` と分かるので EPE を測れる）。準備が整ったので、次節からはこのデータの上で手法を 1 つずつ積み上げていきます。

## 2. フレーム差分 — 一番素朴な動体検出

動きを取り出す最もシンプルな方法は、**連続する 2 枚のフレームを引き算する**ことです。動いていない部分は引き算するとほぼ 0 になり、動いた部分だけに大きな値が残ります。この引き算には、OpenCV の `cv2.absdiff(a, b)` を使います。これは `|a - b|` を**飽和演算**で計算する関数で、`uint8` の素朴な引き算で起きる**ラップアラウンド**（255 を超えると 0 に戻る、負だと巻き上がる）を避けてくれます。あとは差分画像をグレースケール化し、`cv2.threshold` で 2 値化すれば「動いた所＝白」のマスクが得られます。

次のコードが、`01_frame_diff_bgsub.py` におけるフレーム差分の核心です。閾値は固定でもよいのですが、ここでは**大津の自動閾値**（`THRESH_OTSU`）に任せて「動いた／動かない」の境を自動決定しています。

```python
diff = cv2.absdiff(a, b)                       # |a - b| を飽和演算で
gray = cv2.cvtColor(diff, cv2.COLOR_BGR2GRAY)
_, fg = cv2.threshold(gray, 0, 255, cv2.THRESH_BINARY | cv2.THRESH_OTSU)
fg = cv2.morphologyEx(fg, cv2.MORPH_OPEN, KERNEL)   # ごま塩ノイズを除去
```

フレーム差分の弱点は、コードを実行するとすぐに分かります。物体は動いた**縁（へり）だけ**が光り、内部はフレーム間で色が変わらないため差分が 0 になって**穴が空く**のです（`01_framediff_mask.png` を見ると、物体が輪っか状に検出されています）。しかも「今と直前」しか比べないので、**物体が一瞬止まると消えてしまう**という弱点もあります。それでも計算が極めて軽く、実装が数行で済むため、「動きがあったか／なかったか」を雑に検知する用途（簡易モーション検知）では今でも現役です。そして、この穴の問題を解決するのが次の「背景との差分」です。

## 3. 静止背景との差分とその限界

フレーム差分の「縁だけ問題」は、比較相手を**直前のフレーム**から**動く物体が写っていない背景画像**に変えるだけで解決します。背景には物体が無いので、現在フレームから背景を引けば**物体の中身まで丸ごと**差分に残り、輪っかではなく塗りつぶされた塊が取れます。`01_frame_diff_bgsub.py` では最初のフレームを背景の代用に固定し、`cv2.absdiff(target, background)` で前景を抜いています。さらに `MORPH_OPEN`（小ノイズ除去）に続けて `MORPH_CLOSE`（穴埋め）をかけ、塊として整えます。

ところが、この「背景 1 枚固定」方式には実務で致命的な弱点があります。**背景が少しでも変わると全部壊れる**のです。たとえば屋外では、雲で照明が変わり、木が風で揺れ、カメラがわずかに振動するだけで、背景との差分が至る所で立ってしまいます。さらに合成データでも見える罠として、固定した背景（最初のフレーム）に**写り込んでいた物体の初期位置**がいつまでも「背景」として引かれ続けるため、物体が動くと「今の位置」と「最初の位置」の**両方が検出される（ゴースト）**現象が起きます。

```python
background = frames[0]                          # 物体が左端にいる絵を背景の代用に
diff = cv2.absdiff(frames[25], background)
gray = cv2.cvtColor(diff, cv2.COLOR_BGR2GRAY)
_, fg = cv2.threshold(gray, 30, 255, cv2.THRESH_BINARY)
```

要するに「背景は時間とともにゆっくり変わる」「最初の 1 枚を背景と決めつけるのは乱暴」という現実に、固定背景は耐えられないのです。そこで求められるのは、**過去フレームから背景を“学習し続ける”仕組み**——すなわち背景を 1 枚の静止画ではなく画素ごとの統計モデルとして持ち、ゆっくりした変化には追従しつつ、急に現れた物体だけを前景とみなす方式です。それを実現するのが、次節の MOG2 / KNN です。

## 4. 背景差分の実用版 — MOG2 と KNN

OpenCV 本体（contrib 不要）には、背景を統計的に学習する背景差分器が 2 つ同梱されています。一方の **MOG2**（`createBackgroundSubtractorMOG2`）は各画素の色の分布を**混合ガウス分布**でモデル化し、もう一方の **KNN**（`createBackgroundSubtractorKNN`）は近傍法で「最近の値の集まり」から背景らしさを判定します。どちらも `subtractor.apply(frame)` を**フレームを順に与えるたびに呼ぶ**と、内部で背景モデルを更新しながら前景マスクを返します。ここで重要なのは、これらが**履歴で背景を学ぶ**以上、何枚か `apply` して「慣らし運転」を済ませてはじめて前景が安定するという点です。当然、1 枚だけ渡しても意味がありません。

```python
mog2 = cv2.createBackgroundSubtractorMOG2(history=200, varThreshold=25,
                                          detectShadows=True)
for f in frames:               # フレームを順に与えると背景モデルが育つ
    fgmask = mog2.apply(f)     # 前景=255・背景=0・影=127（detectShadows=True 時）
_, fg = cv2.threshold(fgmask, 200, 255, cv2.THRESH_BINARY)   # 影(127)を 0 に落とす
```

`detectShadows=True` にすると、影を**グレー値 127**で別扱いして返してくれます。影をそのまま前景に含めると物体が不自然に大きくなるため、上のように `200` で閾値を切って影を落とすのが定石です。また MOG2 と KNN はどちらも「背景の微小なゆらぎ（ノイズ・わずかな揺れ）」に頑健で、固定背景方式のゴーストも自然に解消されます。一般に **MOG2 は速くてメモリ効率が良く、KNN は画素数が少ない場面で頑健**といわれますが、まずは MOG2 を既定にし、うまくいかなければ KNN を試す、という順序で十分です。

前景マスクが得られたら、最後に**塊を矩形にまとめて「動体検出」の形に整えます**。具体的には、`cv2.findContours` で輪郭を取り（OpenCV 4 系の返り値は `(contours, hierarchy)` の**2 つ**——3 系の 3 つ返しサンプルをそのまま使うと `ValueError` になります）、面積が小さすぎる輪郭をノイズとして捨て、`cv2.boundingRect` で外接矩形を描きます。`01_frame_diff_bgsub.py` を実行すると、`01_mog2_boxes.png` で動くスプライトと緑円だけに緑枠が付き、静止ランドマークは無視されることが確認できます。以上の流れを踏まえ、下の表でここまでの 3 方式を整理します。

| 方式 | 取れるもの | 強み | 弱み | 主な用途 |
| --- | --- | --- | --- | --- |
| フレーム差分（連続2枚） | 動いた**縁**だけ | 最軽量・数行 | 中身に穴・止まると消える | 雑なモーション検知 |
| 静止背景との差分（1枚固定） | 物体の**中身**も | 前景を塗れる | 背景変化に脆い・ゴースト | 背景が完全固定の室内 |
| **MOG2 / KNN** | 物体の**中身**も | 背景変化に頑健・影分離 | 慣らし運転が要る | 監視・入退室・交通など実務 |

この表のとおり、下に行くほど賢く・頑健になり、実務の動体検出はまず MOG2 から入るのが定石です。さて、ここまでで「**前景がどこにあるか**」は取れました。次に知りたいのは「**それがどっちへどれだけ動いたか**」——いよいよオプティカルフローに進みます。

## 5. オプティカルフローとは — 輝度一定と開口問題

**オプティカルフロー（optical flow）**は、連続フレーム間で**各点がどの向きにどれだけ動いたか**を表す 2 次元ベクトル場 `(u, v)` です。背景差分が「動いた領域」を二値で抜くのに対し、フローは「動きの**方向と大きさ**」という連続量を与えます。そして、すべての古典フローは **輝度一定仮定（brightness constancy）**——「同じ物理点は、フレームが変わっても明るさが変わらない」——の上に成り立ちます。この仮定 1 本から `Ix·u + Iy·v + It = 0`（オプティカルフロー拘束方程式）が導かれ、各手法はこれを解くための追加仮定を置きます。

ここで、古典フローの本質的な弱点が 2 つ浮かび上がります。1 つ目は**開口問題（aperture problem）**です。1 枚の拘束式に未知数が `u, v` の 2 つあるため、1 画素だけでは動きを決められません。とくに**のっぺりしたエッジ上**では「エッジに沿う方向の動き」が原理的に観測できません（細い窓から眺めると、縞が斜めに動いても真横に動いても同じに見えるのと同じです）。だからこそ追跡には**角（コーナー）**が向いており、第4回・第5回で学んだ `goodFeaturesToTrack`（Shi-Tomasi コーナー）が疎フローの起点に使われます。2 つ目は**大きな動き**です。輝度一定は「近傍では動きが小さい」ことを前提とするため、速い動きには**画像ピラミッド**（粗い解像度から段階的に解く）で対処します。

古典フローには「疎（sparse）」と「密（dense）」の 2 系統があります。**疎フロー（Lucas-Kanade）**は「**選んだ少数の点だけ**」を追うので軽くて速く、一方の**密フロー（Farnebäck）**は「**全画素**」の動きを推定するので情報は豊かですが重くなります。どちらを選ぶかは目的次第で、「特定の点・物体を追いたい」なら疎、「画面全体の動きの分布を見たい・領域ごとに動きを比べたい」なら密、というのが基本的な使い分けです。以下、次の 2 節で順に実装していきます。

## 6. Lucas-Kanade 疎オプティカルフロー — 点を選んで追う

**Lucas-Kanade 法（LK）**は「**注目点の小さな近傍では、みんな同じ動きをする**」と仮定することで開口問題を回避します。なぜなら、窓内の複数画素ぶんの拘束式を連立させれば `u, v` が一意に解けるからです。OpenCV では、まず `cv2.goodFeaturesToTrack` で追跡しやすい角を選び、次に `cv2.calcOpticalFlowPyrLK`（Pyr = ピラミッド版で大きな動きにも強い）でその点が次フレームのどこへ動いたかを求めます。返り値は `(p1, status, err)` の 3 つで、**`status` が 0/1 の「追えたかフラグ」**、`err` が誤差です。ここでは**`status==1` の点だけを残す**のが鉄則で、見失った点を使い続けると軌跡が暴れてしまいます。

```python
p0 = cv2.goodFeaturesToTrack(gray_prev, maxCorners=200, qualityLevel=0.05,
                             minDistance=7, blockSize=7)   # 追跡の起点になる角
p1, status, err = cv2.calcOpticalFlowPyrLK(gray_prev, gray, p0, None, **LK_PARAMS)
good_new = p1[status.ravel() == 1]      # 追えた点の新位置だけ残す
good_old = p0[status.ravel() == 1]
```

`02_optical_flow_lk.py` は、このステップをフレーム列全体で繰り返し、各点について「前フレームの位置→今の位置」の線分を描き足して**軌跡（トラック）**を伸ばします。このとき、毎フレーム生き残った点を次の起点に更新するのがポイントです。実行すると `02_lk_tracks.png` から、動くスプライト上の点が**長い波打つ軌跡**を描く一方、背景の静止ランドマーク上の点は**ほとんど線を引かない**様子が一目で分かります。さらにコードの `[2]` セクションでは 1 フレーム分の移動量を集計しており、本講座の合成データでは追跡できた 23 点のうち **14 点が動く点（>0.7px）・9 点がほぼ静止**と、数値の上でも動/静が切り分けられます。

LK の使いどころは「**追いたい点が決まっている**」場面です。手作業や検出器で初期点を与え、それをフレーム間で安価に追う使い方で、カメラ動揺の推定、関心領域の追跡、後段トラッカの動き予測などに使われます。逆に、画面のどこに何個動く物体があるか分からないときや、全体の動きの「絵」が欲しいときは、次の密フローが向きます。なお LK は古典手法であるため、**遮蔽（点が物体の陰に隠れる）**や**大きく速い動き・テクスチャの無い領域**では点を見失います。したがって、`status` を必ずチェックし、点が減ってきたら `goodFeaturesToTrack` で補充する、という運用が実務の定石です。

## 7. Farnebäck 密オプティカルフロー — 全画素を塗る

**Farnebäck 法**は、各画素の近傍を**2 次多項式で近似**し、その係数の変化から動きを解くことで、**全画素**の `(u, v)` を一気に求める密フローです。呼び出しは `cv2.calcOpticalFlowFarneback(prev_gray, next_gray, None, 0.5, 3, 15, 3, 5, 1.2, 0)` の正準形で行い、引数は順に `pyr_scale=0.5`（各段で半分に縮小）, `levels=3`（ピラミッド段数）, `winsize=15`（窓の大きさ＝大きいほど大きな動きに強いがぼやける）, `iterations=3`, `poly_n=5`, `poly_sigma=1.2`, `flags=0` です。出力は `(H, W, 2)` の `float32` 配列で、最後の次元が各画素の `u, v` になります。なお入力は**グレースケール**である必要があります。

密フローは「全画素にベクトルがある」ため、そのままでは目で見られません。そこで定番となるのが **HSV 配色での可視化**です——具体的には**色相(H)＝動きの向き**、**明度(V)＝動きの大きさ**、彩度(S)＝最大、に割り当てます。手順としては、`cv2.cartToPolar` で `(u, v)` を「大きさ・角度」に変換し、角度を 0–179（OpenCV の H レンジ）に、大きさを 0–255 に正規化して HSV 画像を作り、`cv2.cvtColor(..., COLOR_HSV2BGR)` で色画像にします。本講座では、この処理を `cv_helpers.flow_to_bgr()` が担います。

```python
mag, ang = cv2.cartToPolar(flow[..., 0], flow[..., 1])
hsv[..., 0] = (ang * 180 / np.pi / 2)            # 向き → 色相(0-179)
hsv[..., 1] = 255
hsv[..., 2] = cv2.normalize(mag, None, 0, 255, cv2.NORM_MINMAX)   # 大きさ → 明るさ
bgr = cv2.cvtColor(hsv, cv2.COLOR_HSV2BGR)
```

`03_optical_flow_farneback.py` を実行すると、`03_farneback_hsv.png` では**動く物体の領域だけが鮮やかに色づき**（向きごとに違う色）、静止した背景は**黒**（大きさ 0）になります。本講座の合成シーンでは、動きの大きさが最大 6.74px・平均 0.45px（＝物体の所だけ立つ）と表示されます。また `03_farneback_arrows.png` は同じフローを格子状の**矢印**で描いたもので、HSV の色が「どっち向き」かを直感的に確認できます。これを `03_flow_color_wheel.png`（カラーホイールの凡例）と見比べれば、どの色がどの向きかを読み解けます。総じて密フローは「画面全体の動きの分布」を見たいとき——動き領域のセグメンテーション、動画安定化、動き特徴量の抽出など——に向きますが、LK より**ずっと重い**ので、CPU では解像度を落とす・必要なフレームだけ計算する、といった工夫が要ります。

## 8. 終点誤差 EPE — フローの良し悪しを数値で測る

「フローが正しく出たか」を見た目だけで判断するのは危険です。そこでフローの精度を測る標準指標として使われるのが**終点誤差（EPE: End-Point Error）**——推定したフローベクトルの**終点**と、真のフローの終点との**ユークリッド距離**を、画素ごとに測って平均したものです。当然、値が小さいほど良いフローです。ただし通常は「真のフロー」が手に入らないため定量評価は難しく、本格的なベンチマークは**深層フロー RAFT を扱う第27回**で行います。そこで本章では、合成データの強みを使って **EPE の概念だけ**を先取りして体験します。

`cv_helpers.make_translating_pair()` は、大きなテクスチャ画像から「位置をずらした 2 つの窓」を切り出すことで、**全画素が `(dx, dy)` だけ動いた**画像ペアを作ります。この場合は真のフローが完全に分かっているので、Farnebäck の推定フローと突き合わせて EPE を計算できます。

```python
a, b, shift = make_translating_pair(shift=(6, 3))   # 全画素が (6,3) 動くペア
flow = cv2.calcOpticalFlowFarneback(gray_a, gray_b, None, 0.5, 3, 15, 3, 5, 1.2, 0)
gt = np.zeros_like(flow); gt[..., 0], gt[..., 1] = shift   # 真のフロー
epe = np.linalg.norm(flow - gt, axis=2)             # 画素ごとの終点誤差
print(epe.mean())                                   # → 0.026 px（ほぼ一致）
```

`03_optical_flow_farneback.py` の `[2]` セクションは、真のシフト `(6, 3)` に対して **EPE 平均 0.026px** という極めて小さい値を出し、`03_farneback_epe.png` に入力ペアと EPE マップ（誤差の空間分布）を保存します。EPE がほぼ 0 だということは、Farnebäck がこの素直な平行移動をほぼ完璧に復元できた、という意味にほかなりません。ここで体に入れてほしいのは「**真値があれば、フローは距離で客観評価できる**」という発想です。実画像では真値が無いので EPE は測れませんが、第27回の深層フローでは、まさにこの EPE をベンチマークデータ上で測ってモデルを比較します。本章はその予習として、指標の定義と「合成なら測れる」という性質を押さえておきましょう。

## 9. meanshift — 色ヒストグラムで物体を追う

ここまでのフローが「**動き**で追う」手法だったのに対し、**meanshift / camshift** は「**色（見た目）**で追う」手法です。発想はこうです——まず追跡対象の**色ヒストグラム**（OpenCV では HSV の**色相 H**を使うのが定番）を 1 回だけ作り、これを「対象の色モデル」とします。次に、各フレームを `cv2.calcBackProject`（**バックプロジェクション**）で「**その色らしさ**の確率マップ」に変換します。すると、対象と同じ色の画素は明るく、違う色の画素は暗くなります。あとは、この確率マップ上で**窓を確率の山の頂上へ滑らせていく**だけ——これが平均値シフト（mean shift）です。

```python
roi_hist = cv2.calcHist([hsv_roi], [0], roi_mask, [16], [0, 180])  # 対象の色モデル
cv2.normalize(roi_hist, roi_hist, 0, 255, cv2.NORM_MINMAX)
# 各フレームで:
prob = cv2.calcBackProject([hsv], [0], roi_hist, [0, 180], 1)      # 色らしさマップ
_, window = cv2.meanShift(prob, window, term_crit)                 # 窓を密度の山へ
```

`04_meanshift_camshift.py` は、合成フレームの**緑の円**を対象に、`cv_helpers.green_window()` が返す初期窓から色相ヒストグラムを作り、全フレームを meanShift で追跡します。実行すると `04_meanshift_trace.png` に円の中心の軌跡が描かれ、`[1]` セクションは初期窓 `(25,153,30,29)` から最終窓 `(255,167,30,29)` へと窓が**横方向に移動**したことを示します。さらに `04_backproject.png` を見ると、確率マップ上で緑円だけが白く光っており（色追跡が「色らしさ」を頼りにしている証拠）、追跡の根拠が一目で分かります。

ただし出力をよく見ると、**窓のサイズは最初から最後まで一定の `30×29`** のままです。これが meanshift の本質的な制約で、**対象が近づいて大きく写っても窓は大きくなりません**。本章の緑円は半径が増えていくため、後半は窓が円より小さくなり、対象の一部しか囲めなくなります。これを解決するのが、次の camshift です。なお色追跡には、もう一つ別の弱点もあります——**背景に似た色があると窓が引っ張られる**ことです。色だけを頼りにする以上、対象と紛らわしい色の領域に吸い寄せられやすいのです。

## 10. camshift — サイズと回転まで対象に合わせる

**camshift（Continuously Adaptive Mean Shift）**は、meanshift を毎フレーム回した上で、さらに**窓のサイズと向き（回転）まで対象の広がりに合わせて更新**します。`cv2.CamShift` の返り値は `(rot_rect, window)` で、`rot_rect = ((cx, cy), (w, h), angle)` は**回転を含む矩形**です。確率マップ上の「対象が占める領域の広がり（モーメント）」から窓の大きさと傾きを推定し直すので、対象が拡大・縮小・回転しても枠がしっかり追従します。あとは `cv2.boxPoints(rot_rect)` で回転矩形の四隅を得て `cv2.polylines` で描けば、傾いた枠を可視化できます。

```python
rot_rect, window = cv2.CamShift(prob, window, term_crit)
pts = cv2.boxPoints(rot_rect).astype(np.int32)   # 回転矩形の四隅
cv2.polylines(frame, [pts], True, (0, 255, 255), 2)
```

`04_meanshift_camshift.py` の `[2]` セクションを実行すると、最初は `≈ (30, 30)` だった窓サイズが最後には `≈ (50, 50)` へと**大きくなり**、`04_camshift_snapshots.png` では緑円の成長に合わせて黄色い枠が膨らんでいく様子が確認できます。これこそが meanshift との決定的な差です。以下、下の表に 2 手法を整理します。

| 手法 | 窓サイズ | 窓の回転 | 追従できる変化 | 出力 |
| --- | --- | --- | --- | --- |
| meanShift | **固定** | なし | 位置の移動のみ | `(x, y, w, h)` |
| CamShift | **対象に追従** | あり | 位置・**拡縮**・**回転** | 回転矩形 `((cx,cy),(w,h),angle)` |

camshift はもともと**顔・手の追跡**（肌色ヒストグラムで顔を追い、近づけば枠が大きくなる）で有名になった手法です。ただし両者に共通する前提は「**対象の色分布がフレーム間で大きく変わらない**」ことであり、照明が大きく変わって色がずれたり、対象が向きを変えて別の色の面が見えたりすると破綻します。だからこそ実務では、HSV の**色相だけ**を使い（明度の変化に多少強い）、彩度・明度が低すぎる画素を `inRange` で除外してヒストグラムを作る、という前処理が効きます。本章のコードも、この定石に従っています。

## 11. 古典 vs 深層 — 何を後の章へ引き継ぐか

ここまでの古典手法は、すべて「**学習なし**」であり、前提が透けて見える代わりに、その前提が崩れると素直に壊れます。そして、この限界こそが後の深層手法へ橋を架けるポイントになります。まず**フロー**について、本章の Farnebäck は「輝度一定＋局所多項式近似」という古典の枠内で全画素フローを出しましたが、テクスチャの無い領域・大きな遮蔽・速い動きには弱いものでした。これに対し**第27回の RAFT**は、ニューラルネットが「対応関係」を学習で見つけるため、こうした難所で古典を大きく上回ります。そして、本章で触れた **EPE** が、まさにその優劣を測る共通のものさしになります。

**追跡**についても対比は明確です。本章の meanshift/camshift は「単一物体を色で追う」古典トラッカで、対象を 1 つだけ、色を頼りに追います。これに対し**第28回の ByteTrack / DeepSORT**は、物体検出器（YOLO 等）の出力を入力として、**多数の物体にまたがって ID を一貫させる**多物体追跡です。とくに DeepSORT は外見特徴（深層埋め込み）まで使って ID の取り違えを減らします。この「背景差分（本章）→ 検出 → 多物体追跡」という流れのなかで、「動きを抜く最初の一手」を担うのが本章の位置づけです。以下、下の表で全体を俯瞰します。

| 課題 | 本章（古典・学習なし） | 後の章（深層・学習あり） | 古典の使いどころ |
| --- | --- | --- | --- |
| 前景抽出 | フレーム/背景差分・MOG2/KNN | （検出ベースのマスク） | 固定カメラの動体検知。軽量・即動く |
| 疎な動き | Lucas-Kanade | — | 既知点の安価な追跡・動揺推定 |
| 密な動き | Farnebäck | **RAFT（第27回）** | 全体の動き分布をざっと見る・前処理 |
| 物体追跡 | meanshift / camshift | **ByteTrack/DeepSORT（第28回）** | 単一・色が特徴的な対象を CPU で軽く追う |

この表のとおり、古典手法は「消えた」のではなく、「**軽量・即動く・前処理**」という役割で生き残っています。深層が常に正解とは限らず、固定カメラの監視なら MOG2 が一番安い、初期化済みの単一対象を CPU だけで追うなら camshift で十分、といった判断ができることこそ中級者の条件です。だからこそ、深層の章に進む前に、まず古典で「動きとは何か」を手で掴んでおくことが、後の理解を一段深くしてくれます。

## 12. よくあるエラーと対処（チェックリスト）

最後に、この章でつまずきやすい点を「症状 → 原因 → 対処」の形で一覧にまとめます。実装中に詰まったら、まずここを見てください。多くの不具合は、この数個の原因に集約されるはずです。

| 症状 | ほぼ確実な原因 | 対処 |
| --- | --- | --- |
| 差分マスクが物体の輪っかだけになる | フレーム差分は縁しか出ない（中身は色が同じで差 0） | 背景差分（MOG2/KNN）に切替。または `MORPH_CLOSE` で穴埋め |
| 背景差分の前景が全面ノイズだらけ | 慣らし運転前／影を前景に含めた | フレームを順に `apply` して背景を育てる。影(127)を閾値で落とす |
| `findContours` で `ValueError` | OpenCV 4 系は **2 つ返し** `(contours, hierarchy)` | `contours, _ = cv2.findContours(...)` と受ける（3 系は 3 つ返し） |
| LK の軌跡が突然飛ぶ・暴れる | 見失った点（`status==0`）を使い続けた | `p1[status.ravel()==1]` で追えた点だけ残す。減ったら点を補充 |
| LK が動きを拾わない | のっぺりした領域に点を置いた（開口問題） | `goodFeaturesToTrack` で角を選ぶ。`winSize`/`maxLevel` を上げる |
| Farnebäck で `(-215) ... type` エラー | カラー画像をそのまま渡した | `cv2.cvtColor(..., COLOR_BGR2GRAY)` でグレースケールにして渡す |
| HSV フロー図の色が変・赤青反転 | `flow_to_bgr` で `HSV2BGR` を忘れ／matplotlib に BGR を渡した | `cvtColor(hsv, HSV2BGR)`、matplotlib には `BGR2RGB` してから渡す |
| meanshift の窓が対象より小さいまま | meanShift は**窓サイズ固定** | サイズ追従が要るなら `cv2.CamShift` を使う |
| 色追跡が背景に吸い寄せられる | 背景に対象と似た色がある／S,V の低い画素を含めた | `inRange` で低彩度・低明度を除外。H だけでヒスト作成 |
| `cv2.imshow` で固まる/エラー | headless 版に imshow は無い | `cv2.imwrite` か matplotlib(Agg) で保存して確認する |

この表の項目が、本章で時間を取られる原因のほぼ全てです。逆に言えば、これらを自分の言葉で説明でき、回避コードを書けるようになれば、この章のゴールに到達したと言えます。

## まとめ

この章では、学習を使わない古典的な動き解析の四本柱を、合成した連番フレームの上で一通り自分の手で書きました。具体的には、**フレーム差分→静止背景差分→MOG2/KNN** と段階的に頑健化して前景マスクと外接矩形を出し、**Lucas-Kanade** で選んだ特徴点の軌跡を追い（動く点と静止点を移動量で切り分け）、**Farnebäck** で全画素フローを HSV と矢印で可視化して**終点誤差 EPE** の概念に触れ、**meanshift/camshift** で色ヒストグラムによる単一物体追跡（窓サイズ固定 vs サイズ・回転追従）を実装しました。そして同時に、各手法が置く仮定（背景静止・輝度一定・色分布不変）と、それが崩れる場面での壊れ方も体感しました。

ここで身につけた「**隣り合うフレームを比べて動きを取り出す**」という発想と、古典手法の前提・限界を見立てる目は、次の章以降——リアルタイム/ストリーム処理（第11回）、深層フロー RAFT（第27回）、多物体追跡 ByteTrack/DeepSORT（第28回）——の理解に直接効いてきます。深層手法は古典の弱点を学習で埋めるものですが、それでも「軽量・即動く・前処理」という役割で古典は今も現役です。まずは演習を自力で全問 PASS させ、`absdiff`／`status==1` の取り出し／`HSV2BGR` 可視化／meanShift と CamShift の違い、という定石を手に馴染ませてから次へ進んでください。

## 🛠 章末ミニプロジェクト — 合成動画の総合「動き解析レポート」

ここまでの四本柱（**背景差分・疎フロー LK・密フロー Farnebäck・色追跡 CamShift**）を、**1 本のパイプライン**に統合する総合課題です。`mini_project.py` を実行すると、合成した連番フレームに対して次の処理が一気に走ります。これは「読み物」ではなく**完成形**であり、実運用では `make_motion_frames()` を実カメラの `VideoCapture` ループに差し替えるだけで、そのまま「固定カメラの動体検出＋追跡」のひな形になります。

1. **背景差分（MOG2）**: 各フレームを `apply` して背景モデルを育てつつ前景マスクを得て、影（127）を落とし、形態学で整え、輪郭→外接矩形で**動体を緑枠**にする。
2. **疎フロー（LK）**: 1 枚目で選んだ角を全フレーム `calcOpticalFlowPyrLK` で追跡し、`status==1` の点だけ残して**軌跡**を描き、現フレームの点を**青点**で重ねる。
3. **密フロー（Farnebäck）**: 既知シフトのペアで**終点誤差 EPE** を測り（合成なので真値が分かる）、シーンのフローを **HSV 配色**で可視化する。
4. **色追跡（CamShift）**: 緑円の色ヒストグラムを作り、`calcBackProject` の確率マップ上で**回転矩形（黄枠）**を追従させ、**窓面積の成長率**を数値化する（半径が増えるので 1.0 超になる）。
5. **統合可視化＋計測**: 各フレームに「動体枠＋LK 点＋追跡窓」を重ねた**動画**を `VideoWriter`（`mp4v`）で書き出し、`time.perf_counter` と移動平均で**処理 FPS**（ソース FPS とは別物）を測る。

なお `digit` 始まりの 01〜04 は import できないため、各アルゴリズムの核心は `mini_project.py` 内に**自己完結**の形で実装しています（合成データ生成と可視化部品だけは `cv_helpers` から借用）。

**到達の目安**: 既知シフト `(6, 3)` の EPE がほぼ 0（合成を正しく復元）、CamShift の窓成長率が概ね 2 倍以上（円の拡大に追従）、そして背景差分が動く 2 物体を概ね拾うこと。出力としては、`outputs/10_classical_video_motion/` に以下が保存されます。

| 生成物 | 内容 |
| --- | --- |
| `mini_project_overlay.mp4` | 全フレームに動体枠＋LK 点＋CamShift 窓＋処理FPS を重ねた統合動画（`VideoWriter` が開けない環境では連番 PNG にフォールバック） |
| `mini_project_overlay_key*.png` | 要所（最初・中間・最後）のフレームを静止画でも保存 |
| `mini_project_flow_hsv.png` | シーンの密フローを HSV 配色で可視化した 1 枚 |
| `mini_project_summary.png` | 前景マスク・LK 軌跡・密フロー・統合オーバレイを 2×2 で並べたまとめ図 |
| `mini_project_metrics.json` | 動体数・追跡点数・EPE・窓成長率・処理 FPS の数値ログ |

```bash

cat outputs/10_classical_video_motion/mini_project_metrics.json
```

## 💡 実践ユースケース集

本章の古典的な動き解析は「学習なし・CPU・即動く」が武器であり、固定カメラの映像から動きを取り出す**現実の小ツール**にそのまま化けます。ここでは代表的な 3 つの応用を、作り方の要点と注意点つきで紹介します。なお最後の 1 つは、実際に動く `use_case.py` として同梱しています。

### ① 動き検知録画（モーションレコーダ）— `use_case.py`（同梱・すぐ動く）

- **何に使うか**: 監視カメラ・玄関カメラ・トラップカメラで定番の機能。映像をずっと録りっぱなしにせず、**動きのあった区間だけ**を自動でクリップに切り出して保存します。容量と後で見る手間を大幅に削減できます。
- **作り方の要点**: 背景差分（MOG2）で各フレームの**前景画素率＝動きスコア**を測り、しきい値を超えた区間を 1 イベントに束ねます。実機同様に**プリロール**（検出の少し前から録る＝頭切れ防止）・**ポストロール／クールダウン**（動きが止まっても数フレーム録り続け、近接イベントを 1 本に統合）を入れ、短すぎるチラつきは捨てます。各イベントを `cv2.VideoWriter`（`mp4v`）でクリップ化します。
- **注意**: 背景差分は**固定カメラ・背景静止**が前提です。手ぶれ・木の揺れ・急な照明変化があると全面が「動き」と判定されやすいので、`MOTION_THRESH` を上げる／関心領域（ROI）に限定する／`history`・`varThreshold` を調整します。
- **実行と確認**:

```bash
uv run python lectures/10_classical_video_motion/use_case.py
cat outputs/10_classical_video_motion/use_case_events.json
```

- **実データの置き方**: `data/10_classical_video_motion/` に**動画**（`*.mp4` / `*.avi` / `*.mov` / `*.mkv`）か**連番画像**（`*.png` / `*.jpg`）を置くと、それを実入力として使います（例: `data/10_classical_video_motion/hallway.mp4`）。**無ければ合成シーン**（静止 → 物体が横切る → 静止、を 2 回）で必ず完走します（`exit 0`）。出力は `outputs/10_classical_video_motion/` に、イベントごとの `use_case_event{k}.mp4`、代表フレーム一覧 `use_case_event_montage.png`、動き量の折れ線＋録画区間を帯で示した `use_case_motion_timeline.png`、イベント表 `use_case_events.json`（録画区間・ピーク動き量・**ストレージ節約率**）が保存されます。
- **拡張アイデア**: しきい値を「前景画素率」から「**最大ブロブ面積**」や「動体の個数」に変えて誤検知を減らす／ROI マスクでドア付近だけ監視する／イベント発生時に通知やサムネイル生成を足して簡易セキュリティ通知へ／背景差分を YOLO 等の検出器に差し替えて「**人が映った時だけ録画**」に高度化／`cv2.VideoCapture(0)` のライブループ＋リングバッファで実カメラの常時監視録画にする。

### ② 通行量・滞留カウント（人流/交通の計測）

- **何に使うか**: 店舗の入店者数、横断歩道や道路の通行量、棚前の滞留時間などの**簡易計測**。
- **作り方の要点**: 背景差分で動体ブロブを外接矩形にし、画面に引いた**仮想ライン**を中心点が横切ったら方向別にカウントします。色や見た目が特徴的な対象なら `CamShift`、複数を区別したいなら中心点の近接対応で簡易追跡 ID を振ると、同一物体の二重カウントを防げます（本格的な多物体追跡は第28回 ByteTrack/DeepSORT へ）。
- **注意**: 影を前景に含めると面積が膨らんで誤カウントします。`detectShadows=True` の影（127）を閾値で落とし、`MORPH_OPEN/CLOSE` で整えること。混雑して物体が重なると 1 ブロブに融合するため、密な場面は検出器ベースに切り替えます。

### ③ 動画ダイジェスト／無音区間スキップ（早送りプレビュー）

- **何に使うか**: 長時間の監視映像やドラレコから、**動きのあるフレームだけ**を抜き出して短いダイジェスト動画やコンタクトシート（要約サムネイル）を作り、確認時間を短縮します。
- **作り方の要点**: ①と同じ動きスコアを使い、しきい値超えのフレームだけを `VideoWriter` に書き出せば「動いた所だけの早送り版」になります。ピーク動きのフレームを各イベントから 1 枚抜けば一覧サムネイルにもできます（`use_case.py` のモンタージュがその最小例）。
- **注意**: フレーム間引きでカクつくので、前後に数フレームの余白（プリ/ポストロール）を残すと見やすくなります。スコアの絶対値はシーンの明るさ・解像度で変わるため、しきい値は映像ごとに調整するか、移動平均からの相対変化で判定します。

## ❓ よくある落とし穴・FAQ・デバッグ

実装中に詰まったら、まずここを見てください。多くの不具合はこの数個の原因に集約されます（第12節の症状別チェックリストと併せて参照）。

- **Q. フレーム差分のマスクが物体の輪っかだけになる。** A. 仕様です。連続 2 枚の差分は**動いた縁**しか出ず、内部は色が同じで差 0 になります。中身まで取りたければ**背景差分（MOG2/KNN）**へ、または `MORPH_CLOSE` で穴埋めします。
- **Q. 背景差分の前景が最初だけ全面真っ白／ノイズだらけ。** A. 背景モデルの**慣らし運転前**です。フレームを順に `apply` して数枚で安定します。1 枚だけ渡しても背景は学習されません。影（127）を前景に含めている場合は `threshold(.., 200, 255, ..)` で落とします。
- **Q. `cv2.findContours` で `ValueError: not enough values to unpack`。** A. OpenCV 4 系は **2 つ返し** `(contours, hierarchy)` です。3 系向けの 3 つ返しサンプルをそのまま使うと落ちます。`contours, _ = cv2.findContours(...)` と受けます。
- **Q. LK の軌跡が突然飛ぶ・暴れる。** A. **見失った点（`status==0`）を使い続けています**。`p1[status.ravel()==1]` で追えた点だけ残し、次の起点に更新します。点が減ったら `goodFeaturesToTrack` で補充します。
- **Q. LK が動きをほとんど拾わない。** A. のっぺりした領域に点を置いた（**開口問題**）か、動きが大き過ぎます。`goodFeaturesToTrack` で角を選び、`winSize`/`maxLevel` を上げてピラミッドを深くします。
- **Q. `calcOpticalFlowFarneback` で `(-215) ... type` エラー。** A. **カラー画像を渡しています**。Farnebäck は**グレースケール**入力が必須。`cv2.cvtColor(..., COLOR_BGR2GRAY)` してから渡します。
- **Q. HSV フロー図の色が変・赤青が反転する。** A. `flow_to_bgr` の最後で `HSV2BGR` を忘れたか、matplotlib に BGR のまま渡しています。可視化は `cvtColor(hsv, HSV2BGR)`、matplotlib には `BGR2RGB` してから渡します。
- **Q. meanShift の窓が対象より小さいまま大きくならない。** A. meanShift は**窓サイズ固定**です。拡縮に追従させたいなら `cv2.CamShift`（回転矩形）を使います。
- **Q. 色追跡が背景に吸い寄せられる。** A. 背景に対象と似た色があるか、S/V の低い画素を色モデルに含めています。`inRange` で低彩度・低明度を除外し、**色相 H だけ**でヒストを作ります。バックプロジェクションを `GaussianBlur` で平滑化してから最尤位置を取ると孤立点に釣られにくくなります。
- **Q. `VideoWriter` で空／壊れた動画ができる、あるいは何も書けない。** A. 出力サイズ `(W, H)` が書き込むフレームと 1px でも食い違うと無言で壊れます。`writer.isOpened()` を必ず検証し、`mp4v`＋`.mp4` か `XVID`＋`.avi` の移植性の高い組み合わせを使い、最後に `release()` します。
- **Q. `cv2.imshow` で固まる／エラーになる。** A. headless 版に `imshow` はありません。`cv2.imwrite`・`VideoWriter`・matplotlib(Agg) で**保存して確認**します。

## 🚀 発展トピック・参考

- **KNN 背景差分・GSOC/LSBP（contrib）**: 本章は本体同梱の MOG2/KNN を使いましたが、`opencv-contrib` には `bgsegm` の GSOC・LSBP などより新しい背景差分があります。同じ `apply` 形式で差し替え比較すると、頑健性とコストのトレードオフが見えます。
- **疎フローの点補充戦略**: LK は遮蔽・速い動きで点を失います。一定数を切ったら `goodFeaturesToTrack` で**再検出して補充**する、グリッド上に強制配置する、といった運用で長時間追跡が安定します。
- **密フローの軽量化**: Farnebäck は重いので、`pyr_scale`/`levels`/`winsize` を下げる、入力を `INTER_AREA` で縮小する、`flags=OPTFLOW_FARNEBACK_GAUSSIAN` を試す、N フレームに 1 回だけ計算する、などで CPU 実時間に寄せられます（第11回の最適化に直結）。
- **DIS オプティカルフロー**: `cv2.DISOpticalFlow_create()` は Farnebäck より速く品質の良い密フローで、CPU 実時間用途で有力です。同じ HSV 可視化に載せて比較すると違いが分かります。
- **EPE 以外の指標**: フロー評価には EPE の他に **Fl-all**（誤差 3px かつ 5% 超の割合）など KITTI/Sintel 系の指標があります。第27回の深層フロー RAFT で、ベンチマークデータ上の定量比較として再登場します。
- **CSRT/KCF 単一物体トラッカ**: 色だけに頼る meanshift/camshift より頑健な古典トラッカ（`cv2.legacy.TrackerKCF_create` 等、contrib 同梱）。検出器なしで 1 物体を追う用途で、camshift の次のステップになります。
- 参考ドキュメント: OpenCV 公式チュートリアル「Optical Flow」 https://docs.opencv.org/4.x/d4/dee/tutorial_optical_flow.html ／「Meanshift and Camshift」 https://docs.opencv.org/4.x/d7/d00/tutorial_meanshift.html ／「Background Subtraction」 https://docs.opencv.org/4.x/d1/dc5/tutorial_background_subtraction.html
