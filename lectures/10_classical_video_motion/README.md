# 第10回 古典的な動画処理 — フレーム差分・背景差分・オプティカルフロー・meanshift/camshift

> トラック: **動画・ストリーム** ／ レベル: **中級** ／ 依存: numpy・opencv-python-headless・pillow・matplotlib のみ（torch/faiss は使いません・追加依存グループなし）

## 🎯 この章のゴール

この章を終えたとき、あなたは「動画の中で**何がどう動いたか**」を、機械学習をいっさい使わずに、OpenCV だけで抽出・可視化できるようになります。扱うのは古典的動画解析の四本柱——**フレーム差分／背景差分**（動いている前景を抜く）、**Lucas-Kanade 疎オプティカルフロー**（選んだ点を追う）、**Farnebäck 密オプティカルフロー**（全画素の動きを推定して HSV で塗る）、そして **meanshift / camshift**（色ヒストグラムで物体を追う）です。いずれも CPU だけで軽快に動き、ネットもカメラも要りません。サンプル映像は各スクリプトが `numpy`/`cv2` で**合成生成**するので、手元に動画が無くても全部が再現できます。

これらは「学習なし」であるがゆえに、**何を仮定しているか・どこで破綻するか**が数式レベルで透けて見えます。背景差分は「背景は静止している」、オプティカルフローは「同じ点の明るさは変わらない（輝度一定）」、meanshift は「対象の色分布は変わらない」——という前提です。本章ではこの前提を意識しながら手を動かし、前提が崩れる場面（背景が動く・照明が変わる・似た色が背景にある）でどう壊れるかまで体感します。これは、のちに学ぶ**深層フロー RAFT（第27回）**や**多物体追跡 ByteTrack/DeepSORT（第28回）**が「古典の何を肩代わりしているのか」を理解する土台になります。

到達点を一言でいえば、**合成した動く図形の連番フレームに対して、背景差分で前景マスクと外接矩形を出し、疎フローで特徴点の軌跡を描き、密フローを HSV と矢印で可視化して終点誤差(EPE)の概念に触れ、meanshift/camshift で色追跡の窓を動かす——という一連の動き解析を自分の手で書き、それぞれの長所・限界・使い分けを説明できる**ことです。フローと色追跡という「動きで追う」「見た目で追う」2 系統の違いも腑に落とします。

## 1. 動画とは静止画の連続 — 本章の合成データ

動画は突き詰めれば**連続した静止画（フレーム）の並び**です。だから動き解析の正体は「**隣り合うフレームを比べる**」ことに尽きます。前回（第9回）は `cv2.VideoCapture` で動画を1枚ずつ読み出す I/O を学びました。本章はその先、読み出した連続フレームから**動き**という情報を取り出します。実データを使わずに学べるよう、本章は共通ヘルパ `cv_helpers.py` の `make_motion_frames()` が、静止した背景の上を 2 つの物体が動く 40 枚のフレーム列を合成します。

合成データには「**答えが分かっている**」という決定的な利点があります。物体の軌道も、背景が静止していることも、平行移動量も、こちらが決めて作っているので、「フローが正しく出たか」「追跡窓が物体に乗っているか」を客観的に確かめられます。`make_motion_frames()` が用意する 2 つの動く物体は、後の各手法に合わせて性格を変えてあります。

- **テクスチャ付きスプライト**（市松模様＋図形）: 角（コーナー）が多く、`goodFeaturesToTrack` が追跡点を拾いやすい。剛体のまま左→右へ並進し、上下に少し揺れる。**疎/密オプティカルフロー**の主役。
- **緑の円**: 背景と色が大きく違うので**色ヒストグラム追跡**に向く。別の軌道で動き、半径が `14→24px` と徐々に増えるので、**camshift のスケール追従**を見せられる。
- **静止ランドマーク**（背景に置いた小さな模様）: 動かない角を提供し、LK で「動く点は長い軌跡・静止点は軌跡なし」という対照を作る。

このように、1 つのシーンに「動く・静止する・色が違う・テクスチャがある」要素を盛り込むことで、4 つの手法すべてを同じデータで体験できます。さらに密フローの定量評価のためだけに、`make_translating_pair()` が**既知の平行移動だけで関係づく画像ペア**を別途生成します（真のフローが全画素 `(dx, dy)` と分かるので EPE を測れる）。次節から、このデータの上で手法を 1 つずつ積み上げます。

## 2. フレーム差分 — 一番素朴な動体検出

動きを取り出す最もシンプルな方法は、**連続する 2 枚のフレームを引き算する**ことです。動いていない部分は引き算するとほぼ 0、動いた部分だけ大きな値が残ります。OpenCV では `cv2.absdiff(a, b)` を使います。これは `|a - b|` を**飽和演算**で計算する関数で、`uint8` の素朴な引き算で起きる**ラップアラウンド**（255 を超えると 0 に戻る、負だと巻き上がる）を避けてくれます。差分画像をグレースケール化し、`cv2.threshold` で 2 値化すれば「動いた所＝白」のマスクになります。

下のコードが `01_frame_diff_bgsub.py` のフレーム差分の核心です。閾値は固定でもよいのですが、ここでは**大津の自動閾値**（`THRESH_OTSU`）で「動いた／動かない」の境を自動決定しています。

```python
diff = cv2.absdiff(a, b)                       # |a - b| を飽和演算で
gray = cv2.cvtColor(diff, cv2.COLOR_BGR2GRAY)
_, fg = cv2.threshold(gray, 0, 255, cv2.THRESH_BINARY | cv2.THRESH_OTSU)
fg = cv2.morphologyEx(fg, cv2.MORPH_OPEN, KERNEL)   # ごま塩ノイズを除去
```

フレーム差分の弱点は、コードを実行するとすぐ分かります。物体は動いた**縁（へり）だけ**が光り、内部はフレーム間で同じ色のため差分が 0 になって**穴が空く**のです（`01_framediff_mask.png` を見ると物体が輪っか状に検出される）。また「今と直前」しか比べないので、**物体が一瞬止まると消えてしまう**。それでも、計算が極めて軽く実装が数行で済むため、「動きがあったか／なかったか」を雑に検知する用途（簡易モーション検知）では今でも現役です。穴の問題を解決するのが、次の「背景との差分」です。

## 3. 静止背景との差分とその限界

フレーム差分の「縁だけ問題」は、比較相手を**直前のフレーム**ではなく**動く物体が写っていない背景画像**に変えると解決します。背景には物体が無いので、現在フレームから背景を引けば**物体の中身まで丸ごと**差分に残り、輪っかではなく塗りつぶされた塊が取れます。`01_frame_diff_bgsub.py` では最初のフレームを背景の代用に固定し、`cv2.absdiff(target, background)` で前景を抜いています。`MORPH_OPEN`（小ノイズ除去）に続けて `MORPH_CLOSE`（穴埋め）をかけ、塊として整えます。

ところがこの「背景 1 枚固定」方式には、実務で致命的な弱点があります。**背景が少しでも変わると全部壊れる**のです。屋外なら雲で照明が変わり、木が風で揺れ、カメラがわずかに振動するだけで、背景との差分が至る所で立ってしまいます。さらに合成データでも分かる罠として、固定した背景（最初のフレーム）に**写り込んでいた物体の初期位置**がいつまでも「背景」として引かれ続けるため、物体が動くと「今の位置」と「最初の位置」の**両方が検出される（ゴースト）**現象が起きます。

```python
background = frames[0]                          # 物体が左端にいる絵を背景の代用に
diff = cv2.absdiff(frames[25], background)
gray = cv2.cvtColor(diff, cv2.COLOR_BGR2GRAY)
_, fg = cv2.threshold(gray, 30, 255, cv2.THRESH_BINARY)
```

つまり「背景は時間とともにゆっくり変わる」「最初の 1 枚を背景と決めつけるのは乱暴」という現実に、固定背景は耐えられません。求められているのは、**過去フレームから背景を“学習し続ける”仕組み**——背景を 1 枚の静止画ではなく、画素ごとの統計モデルとして持ち、ゆっくりした変化には追従しつつ、急に現れた物体だけを前景とみなす方式です。それが次節の MOG2 / KNN です。

## 4. 背景差分の実用版 — MOG2 と KNN

OpenCV 本体（contrib 不要）には、背景を統計的に学習する背景差分器が 2 つ同梱されています。**MOG2**（`createBackgroundSubtractorMOG2`）は各画素の色の分布を**混合ガウス分布**でモデル化し、**KNN**（`createBackgroundSubtractorKNN`）は近傍法で「最近の値の集まり」から背景らしさを判定します。どちらも `subtractor.apply(frame)` を**フレームを順に与えるたびに呼ぶ**と、内部で背景モデルを更新しながら前景マスクを返します。重要なのは、これらは**履歴で背景を学ぶ**ので、何枚か `apply` して「慣らし運転」してから前景が安定する点です。1 枚だけ渡しても意味がありません。

```python
mog2 = cv2.createBackgroundSubtractorMOG2(history=200, varThreshold=25,
                                          detectShadows=True)
for f in frames:               # フレームを順に与えると背景モデルが育つ
    fgmask = mog2.apply(f)     # 前景=255・背景=0・影=127（detectShadows=True 時）
_, fg = cv2.threshold(fgmask, 200, 255, cv2.THRESH_BINARY)   # 影(127)を 0 に落とす
```

`detectShadows=True` にすると、影を**グレー値 127**で別扱いして返してくれます。影をそのまま前景に含めると物体が不自然に大きくなるため、上のように `200` で閾値を切って影を落とすのが定石です。MOG2 と KNN はどちらも「背景の微小なゆらぎ（ノイズ・わずかな揺れ）」に頑健で、固定背景方式のゴーストも自然に解消されます。一般に **MOG2 は速くてメモリ効率が良く、KNN は画素数が少ない場面で頑健**といわれますが、まずは MOG2 を既定にし、うまくいかなければ KNN を試す、という順序で十分です。

前景マスクが得られたら、最後に**塊を矩形にまとめて「動体検出」の形にします**。`cv2.findContours` で輪郭を取り（OpenCV 4 系の返り値は `(contours, hierarchy)` の**2 つ**——3 系の 3 つ返しサンプルをそのまま使うと `ValueError` になります）、面積が小さすぎる輪郭をノイズとして捨て、`cv2.boundingRect` で外接矩形を描きます。`01_frame_diff_bgsub.py` を実行すると、`01_mog2_boxes.png` で動くスプライトと緑円だけに緑枠が付き、静止ランドマークは無視されることが確認できます。下の表で、ここまでの 3 方式を整理します。

| 方式 | 取れるもの | 強み | 弱み | 主な用途 |
| --- | --- | --- | --- | --- |
| フレーム差分（連続2枚） | 動いた**縁**だけ | 最軽量・数行 | 中身に穴・止まると消える | 雑なモーション検知 |
| 静止背景との差分（1枚固定） | 物体の**中身**も | 前景を塗れる | 背景変化に脆い・ゴースト | 背景が完全固定の室内 |
| **MOG2 / KNN** | 物体の**中身**も | 背景変化に頑健・影分離 | 慣らし運転が要る | 監視・入退室・交通など実務 |

この表のとおり、下に行くほど賢く・頑健になります。実務の動体検出はまず MOG2 から入るのが定石です。ここまでで「**前景がどこにあるか**」は取れました。次は「**それがどっちへどれだけ動いたか**」——オプティカルフローに進みます。

## 5. オプティカルフローとは — 輝度一定と開口問題

**オプティカルフロー（optical flow）**は、連続フレーム間で**各点がどの向きにどれだけ動いたか**を表す 2 次元ベクトル場 `(u, v)` です。背景差分が「動いた領域」を二値で抜くのに対し、フローは「動きの**方向と大きさ**」という連続量を与えます。すべての古典フローは **輝度一定仮定（brightness constancy）**——「同じ物理点は、フレームが変わっても明るさが変わらない」——の上に成り立ちます。この仮定 1 本から `Ix·u + Iy·v + It = 0`（オプティカルフロー拘束方程式）が導かれ、各手法はこれを解くための追加仮定を置きます。

ここで古典フローの本質的な弱点が 2 つ出てきます。1 つ目は**開口問題（aperture problem）**です。1 枚の拘束式に未知数が `u, v` の 2 つあるため、1 画素だけでは動きが決められません。とくに**のっぺりしたエッジ上**では「エッジに沿う方向の動き」が原理的に観測できない（細い窓から眺めると、縞が斜めに動いても真横に動いても同じに見える）。だからこそ、追跡には**角（コーナー）**が向いていて、第4回・第5回で学んだ `goodFeaturesToTrack`（Shi-Tomasi コーナー）が疎フローの起点に使われます。2 つ目は**大きな動き**で、輝度一定は「近傍では動きが小さい」前提なので、速い動きには**画像ピラミッド**（粗い解像度から段階的に解く）で対処します。

古典フローには「疎（sparse）」と「密（dense）」の 2 系統があります。**疎フロー（Lucas-Kanade）**は「**選んだ少数の点だけ**」を追い、軽くて速い。**密フロー（Farnebäck）**は「**全画素**」の動きを推定し、情報は豊かだが重い。どちらを選ぶかは目的次第で、「特定の点・物体を追いたい」なら疎、「画面全体の動きの分布を見たい・領域ごとに動きを比べたい」なら密、というのが基本的な使い分けです。次の 2 節で順に実装します。

## 6. Lucas-Kanade 疎オプティカルフロー — 点を選んで追う

**Lucas-Kanade 法（LK）**は「**注目点の小さな近傍では、みんな同じ動きをする**」と仮定して開口問題を回避します。窓内の複数画素ぶんの拘束式を連立させれば `u, v` が一意に解けるからです。OpenCV では `cv2.goodFeaturesToTrack` で追跡しやすい角を選び、`cv2.calcOpticalFlowPyrLK`（Pyr = ピラミッド版で大きな動きにも強い）でその点が次フレームのどこへ動いたかを求めます。返り値は `(p1, status, err)` の 3 つで、**`status` が 0/1 の「追えたかフラグ」**、`err` が誤差です。**`status==1` の点だけを残す**のが鉄則で、見失った点を使い続けると軌跡が暴れます。

```python
p0 = cv2.goodFeaturesToTrack(gray_prev, maxCorners=200, qualityLevel=0.05,
                             minDistance=7, blockSize=7)   # 追跡の起点になる角
p1, status, err = cv2.calcOpticalFlowPyrLK(gray_prev, gray, p0, None, **LK_PARAMS)
good_new = p1[status.ravel() == 1]      # 追えた点の新位置だけ残す
good_old = p0[status.ravel() == 1]
```

`02_optical_flow_lk.py` は、このステップをフレーム列全体で繰り返し、各点について「前フレームの位置→今の位置」の線分を描き足して**軌跡（トラック）**を伸ばします。毎フレーム、生き残った点を次の起点に更新するのがポイントです。実行すると `02_lk_tracks.png` に、動くスプライト上の点が**長い波打つ軌跡**を描き、背景の静止ランドマーク上の点は**ほとんど線を引かない**様子が一目で分かります。コードの `[2]` セクションでは 1 フレーム分の移動量を集計し、本講座の合成データでは追跡できた 23 点のうち **14 点が動く点（>0.7px）・9 点がほぼ静止**、と数値でも動/静が切り分けられます。

LK の使いどころは「**追いたい点が決まっている**」場面です。手作業や検出器で初期点を与え、それをフレーム間で安価に追う——カメラ動揺の推定、関心領域の追跡、後段トラッカの動き予測などに使われます。逆に、画面のどこに何個動く物体があるか分からない、あるいは全体の動きの「絵」が欲しいときは、次の密フローが向きます。なお LK は古典手法なので、**遮蔽（点が物体の陰に隠れる）**や**大きく速い動き・テクスチャの無い領域**では点を見失います。`status` を必ずチェックし、点が減ってきたら `goodFeaturesToTrack` で補充する、という運用が実務の定石です。

## 7. Farnebäck 密オプティカルフロー — 全画素を塗る

**Farnebäck 法**は、各画素の近傍を**2 次多項式で近似**し、その係数の変化から動きを解くことで、**全画素**の `(u, v)` を一気に求める密フローです。`cv2.calcOpticalFlowFarneback(prev_gray, next_gray, None, 0.5, 3, 15, 3, 5, 1.2, 0)` の正準形で呼び、引数は順に `pyr_scale=0.5`（各段で半分に縮小）, `levels=3`（ピラミッド段数）, `winsize=15`（窓の大きさ＝大きいほど大きな動きに強いがぼやける）, `iterations=3`, `poly_n=5`, `poly_sigma=1.2`, `flags=0` です。出力は `(H, W, 2)` の `float32` 配列で、最後の次元が各画素の `u, v` になります。入力は**グレースケール**である必要があります。

密フローは「全画素にベクトルがある」ので、そのままでは見られません。定番が **HSV 配色での可視化**です——**色相(H)＝動きの向き**、**明度(V)＝動きの大きさ**、彩度(S)＝最大、に割り当てます。`cv2.cartToPolar` で `(u, v)` を「大きさ・角度」に変換し、角度を 0–179（OpenCV の H レンジ）に、大きさを 0–255 に正規化して HSV 画像を作り、`cv2.cvtColor(..., COLOR_HSV2BGR)` で色画像にします。本講座では `cv_helpers.flow_to_bgr()` がこの処理を担います。

```python
mag, ang = cv2.cartToPolar(flow[..., 0], flow[..., 1])
hsv[..., 0] = (ang * 180 / np.pi / 2)            # 向き → 色相(0-179)
hsv[..., 1] = 255
hsv[..., 2] = cv2.normalize(mag, None, 0, 255, cv2.NORM_MINMAX)   # 大きさ → 明るさ
bgr = cv2.cvtColor(hsv, cv2.COLOR_HSV2BGR)
```

`03_optical_flow_farneback.py` を実行すると、`03_farneback_hsv.png` で**動く物体の領域だけが鮮やかに色づき**（向きごとに違う色）、静止した背景は**黒**（大きさ 0）になります。本講座の合成シーンでは動きの大きさは最大 6.74px・平均 0.45px（＝物体の所だけ立つ）と表示されます。`03_farneback_arrows.png` は同じフローを格子状の**矢印**で描いたもので、HSV の色が「どっち向き」かを直感的に確認できます。`03_flow_color_wheel.png`（カラーホイールの凡例）と見比べると、どの色がどの向きかを読み解けます。密フローは「画面全体の動きの分布」を見たいとき——動き領域のセグメンテーション、動画安定化、動き特徴量の抽出など——に向きますが、LK より**ずっと重い**ので、CPU では解像度を落とす・必要なフレームだけ計算する、といった工夫が要ります。

## 8. 終点誤差 EPE — フローの良し悪しを数値で測る

「フローが正しく出たか」を見た目だけで判断するのは危険です。フローの精度を測る標準指標が**終点誤差（EPE: End-Point Error）**——推定したフローベクトルの**終点**と、真のフローの終点との**ユークリッド距離**を、画素ごとに測って平均したものです。値が小さいほど良いフローです。ただし通常は「真のフロー」が手に入らないため定量評価は難しく、本格的なベンチマークは**深層フロー RAFT を扱う第27回**で行います。本章では、合成データの強みを使って **EPE の概念だけ**を体験します。

`cv_helpers.make_translating_pair()` は、大きなテクスチャ画像から「位置をずらした 2 つの窓」を切り出すことで、**全画素が `(dx, dy)` だけ動いた**画像ペアを作ります。真のフローが完全に分かっているので、Farnebäck の推定フローと比べて EPE を計算できます。

```python
a, b, shift = make_translating_pair(shift=(6, 3))   # 全画素が (6,3) 動くペア
flow = cv2.calcOpticalFlowFarneback(gray_a, gray_b, None, 0.5, 3, 15, 3, 5, 1.2, 0)
gt = np.zeros_like(flow); gt[..., 0], gt[..., 1] = shift   # 真のフロー
epe = np.linalg.norm(flow - gt, axis=2)             # 画素ごとの終点誤差
print(epe.mean())                                   # → 0.026 px（ほぼ一致）
```

`03_optical_flow_farneback.py` の `[2]` セクションは、真のシフト `(6, 3)` に対して **EPE 平均 0.026px** という極めて小さい値を出し、`03_farneback_epe.png` に入力ペアと EPE マップ（誤差の空間分布）を保存します。EPE がほぼ 0 ということは、Farnebäck がこの素直な平行移動をほぼ完璧に復元できた、という意味です。ここで体に入れてほしいのは「**真値があれば、フローは距離で客観評価できる**」という発想です。実画像では真値が無いので EPE は測れませんが、第27回の深層フローでは、まさにこの EPE をベンチマークデータ上で測ってモデルを比較します。本章はその予習として、指標の定義と「合成なら測れる」という性質を押さえておきます。

## 9. meanshift — 色ヒストグラムで物体を追う

ここまでのフローが「**動き**で追う」手法だったのに対し、**meanshift / camshift** は「**色（見た目）**で追う」手法です。発想はこうです——まず追跡対象の**色ヒストグラム**（OpenCV では HSV の**色相 H**を使うのが定番）を 1 回だけ作って「対象の色モデル」とします。次に、各フレームを `cv2.calcBackProject`（**バックプロジェクション**）で「**その色らしさ**の確率マップ」に変換します。対象と同じ色の画素は明るく、違う色は暗くなります。あとは、この確率マップ上で**窓を確率の山の頂上へ滑らせていく**だけ——それが平均値シフト（mean shift）です。

```python
roi_hist = cv2.calcHist([hsv_roi], [0], roi_mask, [16], [0, 180])  # 対象の色モデル
cv2.normalize(roi_hist, roi_hist, 0, 255, cv2.NORM_MINMAX)
# 各フレームで:
prob = cv2.calcBackProject([hsv], [0], roi_hist, [0, 180], 1)      # 色らしさマップ
_, window = cv2.meanShift(prob, window, term_crit)                 # 窓を密度の山へ
```

`04_meanshift_camshift.py` は、合成フレームの**緑の円**を対象に、`cv_helpers.green_window()` が返す初期窓から色相ヒストグラムを作り、全フレームを meanShift で追跡します。実行すると `04_meanshift_trace.png` に円の中心の軌跡が描かれ、`[1]` セクションは初期窓 `(25,153,30,29)` から最終窓 `(255,167,30,29)` へと**横方向に移動**したことを示します。`04_backproject.png` を見ると、確率マップ上で緑円だけが白く光っているのが分かります（色追跡が「色らしさ」を頼りにしている証拠）。

ただし出力をよく見ると、**窓のサイズは最初から最後まで一定 `30×29`** のままです。これが meanshift の本質的な制約で、**対象が近づいて大きく写っても窓は大きくならない**。本章の緑円は半径が増えていくので、後半は窓が円より小さくなり、対象の一部しか囲めなくなります。これを解決するのが次の camshift です。なお色追跡には別の弱点もあります——**背景に似た色があると窓が引っ張られる**こと。色だけを頼りにするので、対象と紛らわしい色の領域に吸い寄せられやすいのです。

## 10. camshift — サイズと回転まで対象に合わせる

**camshift（Continuously Adaptive Mean Shift）**は、meanshift を毎フレーム回した上で、**窓のサイズと向き（回転）まで対象の広がりに合わせて更新**します。`cv2.CamShift` の返り値は `(rot_rect, window)` で、`rot_rect = ((cx, cy), (w, h), angle)` は**回転を含む矩形**です。確率マップ上の「対象が占める領域の広がり（モーメント）」から窓の大きさと傾きを推定し直すので、対象が拡大・縮小・回転しても枠が追従します。`cv2.boxPoints(rot_rect)` で回転矩形の四隅を得て `cv2.polylines` で描けば、傾いた枠を可視化できます。

```python
rot_rect, window = cv2.CamShift(prob, window, term_crit)
pts = cv2.boxPoints(rot_rect).astype(np.int32)   # 回転矩形の四隅
cv2.polylines(frame, [pts], True, (0, 255, 255), 2)
```

`04_meanshift_camshift.py` の `[2]` セクションを実行すると、最初の窓サイズ `≈ (30, 30)` が最後には `≈ (50, 50)` へと**大きくなり**、`04_camshift_snapshots.png` では緑円の成長に合わせて黄色い枠が膨らんでいく様子が確認できます。これが meanshift との決定的な差です。下の表に 2 手法を整理します。

| 手法 | 窓サイズ | 窓の回転 | 追従できる変化 | 出力 |
| --- | --- | --- | --- | --- |
| meanShift | **固定** | なし | 位置の移動のみ | `(x, y, w, h)` |
| CamShift | **対象に追従** | あり | 位置・**拡縮**・**回転** | 回転矩形 `((cx,cy),(w,h),angle)` |

camshift はもともと**顔・手の追跡**（肌色ヒストグラムで顔を追い、近づけば枠が大きくなる）で有名になった手法です。両者に共通する前提は「**対象の色分布がフレーム間で大きく変わらない**」こと。照明が大きく変わって色がずれたり、対象が向きを変えて別の色の面が見えたりすると破綻します。だから実務では、HSV の**色相だけ**を使い（明度の変化に多少強い）、彩度・明度が低すぎる画素を `inRange` で除外してヒストグラムを作る、という前処理が効きます。本章のコードもこの定石に従っています。

## 11. 古典 vs 深層 — 何を後の章へ引き継ぐか

ここまでの古典手法は、すべて「**学習なし**」で、前提が透けて見える代わりに、前提が崩れると素直に壊れます。この限界こそ、後の深層手法へ橋を架けるポイントです。まず**フロー**について、本章の Farnebäck は「輝度一定＋局所多項式近似」という古典の枠内で全画素フローを出しましたが、テクスチャの無い領域・大きな遮蔽・速い動きには弱い。**第27回の RAFT**は、ニューラルネットが「対応関係」を学習で見つけるため、こうした難所で古典を大きく上回ります。本章で触れた **EPE** が、まさにその優劣を測る共通のものさしになります。

**追跡**についても対比が明確です。本章の meanshift/camshift は「単一物体を色で追う」古典トラッカで、対象を 1 つ・色を頼りに追います。これに対し**第28回の ByteTrack / DeepSORT**は、物体検出器（YOLO 等）の出力を入力に、**多数の物体にまたがって ID を一貫させる**多物体追跡です。DeepSORT は外見特徴（深層埋め込み）まで使って ID の取り違えを減らします。背景差分（本章）→ 検出 → 多物体追跡、という流れの「動きを抜く最初の一手」が本章の位置づけです。下の表で全体を俯瞰します。

| 課題 | 本章（古典・学習なし） | 後の章（深層・学習あり） | 古典の使いどころ |
| --- | --- | --- | --- |
| 前景抽出 | フレーム/背景差分・MOG2/KNN | （検出ベースのマスク） | 固定カメラの動体検知。軽量・即動く |
| 疎な動き | Lucas-Kanade | — | 既知点の安価な追跡・動揺推定 |
| 密な動き | Farnebäck | **RAFT（第27回）** | 全体の動き分布をざっと見る・前処理 |
| 物体追跡 | meanshift / camshift | **ByteTrack/DeepSORT（第28回）** | 単一・色が特徴的な対象を CPU で軽く追う |

この表のとおり、古典手法は「消えた」のではなく「**軽量・即動く・前処理**」という役割で生き残っています。深層が常に正解ではなく、固定カメラの監視で MOG2 が一番安い、初期化済みの単一対象を CPU だけで追うなら camshift で十分、という判断ができることが中級者の条件です。深層の章に進む前に、まず古典で「動きとは何か」を手で掴んでおくことが、後の理解を一段深くします。

## 12. よくあるエラーと対処（チェックリスト）

最後に、この章でつまずきやすい点を「症状 → 原因 → 対処」で一覧にします。実装中に詰まったら、まずここを見てください。多くの不具合は、この数個の原因に集約されます。

| 症状 | ほぼ確実な原因 | 対処 |
| --- | --- | --- |
| 差分マスクが物体の輪っかだけになる | フレーム差分は縁しか出ない（中身は色が同じで差 0） | 背景差分（MOG2/KNN）に切替。または `MORPH_CLOSE` で穴埋め |
| 背景差分の前景が全面ノイズだらけ | 慣らし運転前／影を前景に含めた | フレームを順に `apply` して背景を育てる。影(127)を閾値で落とす |
| `findContours` で `ValueError` | OpenCV 4 系は **2 つ返し** `(contours, hierarchy)` | `contours, _ = cv2.findContours(...)` と受ける（3 系は 3 つ返し） |
| LK の軌跡が突然飛ぶ・暴れる | 見失った点（`status==0`）を使い続けた | `p1[status.ravel()==1]` で追えた点だけ残す。減ったら点を補充 |
| LK が動きを拾わない | のっぺりした領域に点を置いた（開口問題） | `goodFeaturesToTrack` で角を選ぶ。`winSize`/`maxLevel` を上げる |
| Farnebäck で `(-215) ... type` エラー | カラー画像をそのまま渡した | `cv2.cvtColor(..., COLOR_BGR2GRAY)` でグレースケールにして渡す |
| HSV フロー図の色が変・赤青反転 | `flow_to_bgr` で `HSV2BGR` を忘れ／matplotlib に BGR を渡した | `cvtColor(hsv, HSV2BGR)`、matplotlib には `BGR2RGB` してから渡す |
| meanshift の窓が対象より小さいまま | meanShift は**窓サイズ固定** | サイズ追従が要るなら `cv2.CamShift` を使う |
| 色追跡が背景に吸い寄せられる | 背景に対象と似た色がある／S,V の低い画素を含めた | `inRange` で低彩度・低明度を除外。H だけでヒスト作成 |
| `cv2.imshow` で固まる/エラー | headless 版に imshow は無い | `cv2.imwrite` か matplotlib(Agg) で保存して確認する |

この表の項目が、本章で時間を取られる原因のほぼ全てです。逆にこれらを自分で説明でき・回避コードを書けるようになれば、この章のゴールに到達しています。

## まとめ

この章では、学習を使わない古典的な動き解析の四本柱を、合成した連番フレームの上で一通り自分の手で書きました。**フレーム差分→静止背景差分→MOG2/KNN** と段階的に頑健化して前景マスクと外接矩形を出し、**Lucas-Kanade** で選んだ特徴点の軌跡を追い（動く点と静止点を移動量で切り分け）、**Farnebäck** で全画素フローを HSV と矢印で可視化して**終点誤差 EPE** の概念に触れ、**meanshift/camshift** で色ヒストグラムによる単一物体追跡（窓サイズ固定 vs サイズ・回転追従）を実装しました。同時に、各手法が置く仮定（背景静止・輝度一定・色分布不変）と、それが崩れる場面での壊れ方も体感しました。

ここで身につけた「**隣り合うフレームを比べて動きを取り出す**」という発想と、古典手法の前提・限界の見立ては、次の章以降——リアルタイム/ストリーム処理（第11回）、深層フロー RAFT（第27回）、多物体追跡 ByteTrack/DeepSORT（第28回）——の理解に直接効いてきます。深層手法は古典の弱点を学習で埋めるものですが、「軽量・即動く・前処理」という役割で古典は今も現役です。まずは演習を自力で全問 PASS させ、`absdiff`／`status==1` の取り出し／`HSV2BGR` 可視化／meanShift と CamShift の違い、という定石を手に馴染ませてから次へ進んでください。
