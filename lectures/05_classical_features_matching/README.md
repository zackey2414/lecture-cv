# 第5回 特徴点検出とマッチング — SIFT/ORB・BFMatcher/FLANN・テンプレート・Hough

> トラック: **古典CV** ／ レベル: **初級** ／ 依存: numpy・opencv-python-headless・matplotlib のみ（torch/faiss は使いません・追加依存グループなし）

## 🎯 この章のゴール

この章を終えたとき、あなたは「2 枚の画像が同じ物体・同じ場所を写しているかどうかを、コードで判定し定量評価できる」状態になります。鍵になるのは**局所特徴量（local feature）**という考え方です。画像全体を一気に比べるのではなく、角や斑点といった「周囲と区別しやすい小さな目印（キーポイント）」を見つけ、その周りの見た目を数百次元の数値ベクトル（記述子）に符号化し、2 枚の記述子同士を突き合わせる——この一連の流れを、SIFT と ORB という二大手法で自分の手で書けるようになるのが目標です。

同時に、マッチングで必ず混入する誤対応を 2 段構えで落とす定石——**Lowe の比率テスト（0.75）**で曖昧な対応を捨て、**RANSAC**で幾何的に整合しない対応を捨てる——を体得します。さらに「良マッチ数」と「インライア率（inliers / total）」という 2 つの数値でマッチング品質を測り、なぜ比率しきい値が 0.75 あたりに落ち着くのかを、しきい値スイープの実験を通じて自分の目で確かめます。これは後の第6回（ホモグラフィ・パノラマ）やキャリブレーションの直接の土台です。

最後に、特徴点に頼らない素朴な手法——**テンプレートマッチング**と**Hough 変換**——も扱い、その限界（回転・スケール非不変、パラメータへの過敏さ）を実験で痛感します。これらの限界こそが「だから局所特徴量が必要だ」という動機そのものなので、古典 CV の全体像を立体的に理解する回になります。到達点を一言でいえば、**サンプル画像が無くても・GPU が無くても、特徴点マッチングのパイプラインを最初から最後まで一人で書け、その良し悪しを数値で説明できる**ことです。

## 1. なぜ「局所特徴量」なのか — 素朴な照合の限界

2 枚の画像が同じ物体を写しているかを判定する最も素朴な方法は、片方を「テンプレート」として、もう片方の上をピクセル単位で滑らせ、最もよく重なる位置を探すことです（テンプレートマッチング、本章 8 節）。これは対象の見た目・向き・大きさが完全に同じであれば驚くほどうまく動きます。ところが現実のカメラは、少し動けば対象が回転し、近づけば対象が拡大します。素朴な照合は**回転・スケール・視点の変化に対して一切不変でない**ため、こうしたわずかな条件差でたちまち破綻してしまいます。

局所特徴量は、この問題を「画像全体」ではなく「区別しやすい小さな目印の集合」として捉えることで乗り越えます。具体的には、角（コーナー）や斑点（ブロブ）のように周囲と明確に違う点を**キーポイント**として検出し、その点まわりの局所パターンを、回転や明るさの変化に強い形で数値ベクトル（**記述子**）へ符号化します。こうしておけば、対象が回ろうが拡大されようが「目印そのものの見た目」は保たれるので、2 枚の記述子を突き合わせるだけで対応が取れます。

この章で使う SIFT と ORB は、いずれもこの「キーポイント検出＋記述子計算」を一手に引き受けるアルゴリズムです。考え方の核心は共通で、違いは「記述子をどう表現するか（実数か 2 進数か）」と「速度・頑健性のバランス」です。まずはこの大枠——**素朴な照合は変化に弱い → 区別しやすい点を符号化して照合する → それが局所特徴量**——を頭に入れてから、具体的な API に進みます。

## 2. `detectAndCompute` — キーポイントと記述子

OpenCV では、検出器オブジェクトを作って `detectAndCompute(gray, None)` を呼ぶだけで、キーポイント列と記述子行列が同時に得られます。SIFT は `cv2.SIFT_create()`、ORB は `cv2.ORB_create()` で作ります。**SIFT はかつて特許に守られていましたが、その特許はすでに失効し、現在は contrib ではなく本体（main モジュール）に同梱されています**。したがって、古い記事にある `cv2.xfeatures2d.SIFT_create()` という呼び方は時代遅れで、本講座の headless 版（contrib なし）でも `cv2.SIFT_create()` がそのまま使えます。

特徴点検出は**グレースケール画像に対して行う**のが定石です。色そのものではなく明暗の構造（勾配やコーナー）で目印を拾うため、`cv2.cvtColor(img, cv2.COLOR_BGR2GRAY)` で 1 チャンネルにしてから渡します。戻り値の記述子行列は形状 `(N, D)` で、`N` がキーポイント数、`D` が 1 点あたりの次元数です。ここで両手法の決定的な違いが出ます。

```python
gray = cv2.cvtColor(img, cv2.COLOR_BGR2GRAY)
sift = cv2.SIFT_create()
kp, des = sift.detectAndCompute(gray, None)
print(len(kp), des.shape, des.dtype)   # 例: 418 (418, 128) float32
orb = cv2.ORB_create(nfeatures=2000)
kp2, des2 = orb.detectAndCompute(gray, None)
print(len(kp2), des2.shape, des2.dtype)  # 例: 2000 (2000, 32) uint8
```

上の出力が示すように、**SIFT の記述子は 128 次元の浮動小数（`float32`）**で、ベクトル間の近さは普通のユークリッド距離（`NORM_L2`）で測ります。一方**ORB の記述子は 32 バイト＝256 ビットの 2 進列（`uint8`）**で、近さは「何ビット違うか」を数えるハミング距離（`NORM_HAMMING`）で測ります。この「記述子の型 → 使う距離」の対応を取り違えると、マッチングはたちまち無意味な結果になります。スクリプト `01_sift_orb_match.py` は、この 2 手法を同じ画像に適用して並べ、検出点数と記述子の性質を表示します。

## 3. マッチング — `BFMatcher` / `knnMatch` と Lowe の比率テスト

記述子が得られたら、次は画像 1 の各点に対して、画像 2 の中から最も近い記述子を探します。その最も基本的な方法が**総当たり（Brute-Force）マッチャ** `cv2.BFMatcher(normType)` です。`normType` には前節で述べた通り、SIFT なら `cv2.NORM_L2`、ORB なら `cv2.NORM_HAMMING` を渡します。総当たりは小〜中規模なら十分高速かつ正確で、まずこれを使えば間違いありません。

ただ「一番近い点」をそのまま採用すると誤対応が大量に混じります。そこで使うのが **`knnMatch(des1, des2, k=2)`** で、各点について「最も近い点 m」と「2 番目に近い点 n」の 2 つを返させます。そして **Lowe の比率テスト**——`m.distance < 0.75 * n.distance` を満たすものだけ残す——を適用します。直感的には「1 番目が 2 番目を大きく引き離している＝本当に特徴的で信頼できる対応」だけを採用し、「1 番目と 2 番目が僅差＝どっちつかずで怪しい」対応を捨てる、という考え方です。

```python
bf = cv2.BFMatcher(cv2.NORM_HAMMING)          # ORB なら HAMMING
knn = bf.knnMatch(des1, des2, k=2)
good = []
for pair in knn:
    if len(pair) < 2:        # 近傍が1個しか無いペアは比較不能 → 捨てる
        continue
    m, n = pair
    if m.distance < 0.75 * n.distance:
        good.append(m)
```

ここで初学者が必ず踏む罠が、`len(pair) < 2` のチェック省略です。`knnMatch` は、ある点について近傍が 1 個しか見つからないと**長さ 1 のペア**を返すことがあり、これを `m, n = pair` でいきなり展開すると `ValueError` で落ちてしまいます。比率テストを書くときは必ず長さ 2 を確認してから展開してください。`01_sift_orb_match.py` の `ratio_test` 関数と `exercises.py` の演習 1 が、まさにこの定石を扱います。

## 4. `FLANN` と `crossCheck` — もう 2 つの選択肢

総当たりは正確ですが、キーポイントが数千〜数万に増えると遅くなります。そこで**近似最近傍探索**を使う `cv2.FlannBasedMatcher` が用意されています。FLANN は厳密な最近傍を諦める代わりに高速で、大規模なマッチングで威力を発揮します。注意点は、**記述子の型によって内部の索引（index）を変える**ことです。SIFT のような浮動小数記述子には KD-Tree（`algorithm=1`）、ORB のような 2 進記述子には LSH（`algorithm=6`）を指定します。型に合わない index を渡すと、エラーになるか結果が壊れます。

```python
# SIFT（浮動小数）向け: KD-Tree
flann = cv2.FlannBasedMatcher(dict(algorithm=1, trees=5), dict(checks=50))
knn = flann.knnMatch(des1, des2, k=2)   # 後段は BF と同じく比率テスト
```

もう 1 つ、比率テストとは別系統の誤対応除去が **`crossCheck`** です。`cv2.BFMatcher(norm, crossCheck=True)` を作って `match()`（`knnMatch` ではない）を呼ぶと、「画像 1→2 の最近傍」と「画像 2→1 の最近傍」が**互いに一致した対応だけ**を返します。相互に「君が一番近い」と言い合えるペアだけ残す、という対称性に基づく除去です。

実務上の注意は、**比率テストと crossCheck を併用しない**ことです。`crossCheck=True` は内部的に k=1 のマッチングを前提とするため `knnMatch(k=2)` とは相性が悪く、どちらか一方の戦略を選ぶ必要があります。一般には、比率テストの方が調整が効き、誤対応をきめ細かく落とせるため好まれます。`01_sift_orb_match.py` は FLANN と crossCheck の両方を実演し、どちらも BF＋比率テストと近い結果になることを示します。

## 5. `RANSAC` とインライア率 — 品質を数値で測る

比率テストを通っても、なお幾何的にあり得ない対応（外れ値）は残ります。これを落とし、同時に「2 枚の幾何関係」を推定するのが **`cv2.findHomography(src, dst, cv2.RANSAC, 5.0)`** です。RANSAC は「ランダムに少数の対応を選んで仮の変換を作り、それに合う対応が最も多い仮説を採用する」反復法で、外れ値に極めて強いのが特長です。返り値の `mask` は各対応がインライア（1）か外れ値（0）かを示し、`mask.sum()` がインライア数になります。

```python
src = np.float32([kp1[m.queryIdx].pt for m in good]).reshape(-1, 1, 2)
dst = np.float32([kp2[m.trainIdx].pt for m in good]).reshape(-1, 1, 2)
H, mask = cv2.findHomography(src, dst, cv2.RANSAC, ransacReprojThreshold=5.0)
inlier_ratio = int(mask.sum()) / len(good)     # 品質の物差し
```

ここで重要なのが、**`findHomography` は最低 4 組の対応点を必要とする**ことです。良マッチが 4 組未満のときは推定できないので、必ず本数を確認してから呼びます。そして本章の評価指標が**インライア率 = インライア数 / 良マッチ数**です。良マッチ数が「量」を、インライア率が「質（純度）」を表し、この 2 つを併せて見ることでマッチングの良し悪しを客観的に判断できます。

`01_sift_orb_match.py` は SIFT・ORB の両方でこの指標を計算し、`exercises.py` の演習 2 でインライア率の計算を自分で実装します。合成画像は「正解のホモグラフィが分かっている別視点ペア」なので、推定した `H` がどれだけ正解に近いかを、インライア率を通じて間接的に検証できる構造になっています。下の表が 2 段構えの誤対応除去の全体像です。

| 段階 | 手法 | 落とすもの | 必要な前提 |
| --- | --- | --- | --- |
| 1段目 | Lowe 比率テスト（0.75） | 1番目と2番目が僅差の曖昧な対応 | `knnMatch(k=2)` |
| 2段目 | RANSAC（`findHomography`） | 幾何的に整合しない外れ値 | 良マッチ4組以上 |

この 2 段を通すことで、ノイズの多い生のマッチから、信頼できる対応だけが残ります。「1段目で量と純度をある程度整え、2段目で幾何によって仕上げる」という役割分担を意識すると、各手法がなぜ存在するのかが腑に落ちるはずです。

## 6. 比率しきい値スイープ — なぜ 0.75 なのか

「比率テストのしきい値はなぜ 0.75 なのか」は、覚えるより実験で納得するのが近道です。しきい値を**下げる（厳しくする）と良マッチ数は減るが純度は上がり**、**上げる（緩くする）と数は増えるが誤対応も増えてインライア率は下がる**——というトレードオフがあります。0.75 は、十分な対応数を確保しつつ純度を高く保てる経験的なバランス点で、Lowe の原論文以来の定番です。

`01_sift_orb_match.py` はしきい値を 0.5〜0.9 で振り、各値での良マッチ数とインライア率を表で出力します。下は実行例（ORB）です。値が大きくなるほど good が増える一方、インライア率が 1.00 から 0.92 へ少しずつ下がっていく様子が読み取れます。

```text
 ratio   good  inliers  inlier率
  0.50    377      376     1.00
  0.70    920      910     0.99
  0.75   1066     1043     0.98
  0.80   1181     1145     0.97
  0.90   1459     1347     0.92
```

この表のポイントは、**0.75 を超えて緩めると、増える対応のうち外れ値の割合が目に見えて増える**ことです。逆に 0.5 まで締めると純度はほぼ完璧になりますが、難しい視点変化では良マッチが足りず `findHomography` が不安定になります。つまり 0.75 は「数」と「質」の妥協点であり、対象が難しい（視点変化が大きい）ときは少し緩め、誤検出を許せないときは少し締める、という調整の出発点として使うものです。固定の魔法の数字ではなく、トレードオフの中心だと理解してください。

## 7. テンプレートマッチング — 単純さと限界

ここからは特徴点に頼らない素朴な手法です。**テンプレートマッチング** `cv2.matchTemplate(scene, template, method)` は、テンプレート画像をシーン上で 1 ピクセルずつ滑らせ、各位置での「一致度」を相関マップとして返します。最良位置は `cv2.minMaxLoc` で取り出します。ここで手法ごとに**最大が良いのか最小が良いのか**が変わる点に注意が必要です。`TM_CCOEFF_NORMED` / `TM_CCORR_NORMED` は値が大きいほど良いので `maxLoc` を、`TM_SQDIFF_NORMED`（差の二乗和）は小さいほど良いので `minLoc` を採用します。明るさ変化にある程度強い正規化版（`*_NORMED`）を使うのが無難です。

```python
res = cv2.matchTemplate(scene, template, cv2.TM_CCOEFF_NORMED)
min_v, max_v, min_l, max_l = cv2.minMaxLoc(res)
top_left = max_l           # CCOEFF 系は「最大」が答え
```

`02_template_matching.py` は、同じ向き・同じ大きさなら一致度 1.000 でズレ 0px と完璧に当たることを示した後、限界を 2 つ実験します。1 つ目は**回転**で、シーンを 35 度回しただけで一致度が 1.000 から 0.69 へ急落します。2 つ目は**スケール**で、シーンを 1.3 倍に拡大すると固定サイズのテンプレートでは一致が悪くなります。

スケールの問題に対する古典的な対処が**マルチスケール探索**です。テンプレート（またはシーン）を複数の倍率にリサイズしながら総当たりし、最も一致度の高い倍率を採用します。`02_template_matching.py` は倍率 0.6〜1.6 を走査し、正しい 1.30 倍で一致度が 1.000 に回復することを表で示します。縮小には `INTER_AREA`、拡大には `INTER_CUBIC` を使うのが定石です。

```text
 scale   score
  1.00   0.683   ← 単一スケールでは低い
  1.30   1.000   ← 正しい倍率を当てると回復
  1.60   0.428
```

この実験の教訓は明快です。**テンプレートマッチングは「見た目・向き・大きさが同じ」なら最強に簡単だが、回転やスケールには本質的に弱い**。マルチスケールで大きさは吸収できても、回転までは手当てできず、両方に対応しようとすれば組み合わせ爆発も起きます。だからこそ、回転・スケール不変な局所特徴量（SIFT/ORB）が必要になる——という、本章前半への動機づけがここで閉じます。

## 8. Hough 変換 — 投票による直線・円検出とパラメータ過敏性

**Hough 変換**は「パラメータ空間への投票」という古典 CV を象徴する発想です。エッジ上の各点が「自分が通り得る直線（や円）のパラメータ」に票を投じ、票が集まったパラメータを検出結果とします。直線検出では**まず `cv2.Canny` でエッジ画像を作り、それを `cv2.HoughLinesP` に渡す**のが必須の流れです。`HoughLinesP`（確率的ハフ）は線「分」を端点 `[x1, y1, x2, y2]` 付きで返すので、実用的で扱いやすい版です。

```python
edges = cv2.Canny(gray, 50, 150)               # 直線Houghの前段は必ずエッジ画像
lines = cv2.HoughLinesP(edges, 1, np.pi/180, threshold=80,
                        minLineLength=40, maxLineGap=10)
```

円検出 `cv2.HoughCircles(gray, cv2.HOUGH_GRADIENT, ...)` には**1 つ大きな落とし穴**があります。直線とは違い、円検出には**エッジ画像ではなくグレー画像を渡す**のです（内部で Canny と勾配計算を行うため、自分でエッジ化すると二重になって失敗します）。引数 `param1` は内部 Canny の上側しきい値、`param2` は中心の投票しきい値で、**`param2` を上げ過ぎると 1 個も検出されず、下げ過ぎると幻の円が大量に出ます**。

`03_hough_lines_circles.py` はこのパラメータ過敏性を表で可視化します。下は円検出の `param2` スイープの実行例で、30 までは正解の 3 個を検出できるのに、40 で 1 個、60 で 0 個に崩れる様子が分かります。直線側も `threshold` をわずかに変えるだけで本数が大きく振れます。

```text
 param2     円数
     25      3
     30      3      ← ちょうどよい
     40      1
     60      0      ← 高過ぎて全滅
```

この表が伝えるのは、**Hough 変換は前処理（Canny のしきい値）とアルゴリズムのパラメータに極端に敏感**だということです。そのため実画像では、「当たりのパラメータ探し」そのものが仕事になります。一方、対象が直線・円のように数式で書ける幾何形状で、かつパラメータを丁寧に合わせられるなら、Hough は学習不要で頑健に効く強力な道具です。テンプレートや特徴点とは「効く場面」が違う、という使い分けの感覚を持ち帰ってください。

## 9. SIFT と ORB の使い分け（実務）

ここまでの実験を踏まえると、SIFT と ORB の選び方が見えてきます。**SIFT は少ない点数でも高いインライア率を出しやすく、視点変化や回転に頑健**です。精度が最優先で、多少計算時間がかかってもよい場面（オフラインの位置合わせ、高精度なパノラマ合成、キャリブレーション補助など）に向きます。記述子が 128 次元の実数なので、メモリと距離計算のコストは ORB より高めです。

**ORB は特許フリーで、CPU でも非常に高速**です。2 進記述子のハミング距離はビット演算で一瞬に計算でき、点数を多く取っても軽快に動きます。リアルタイム性が要る用途（動画のフレーム間追跡、モバイル/組み込み、SLAM の特徴抽出）で第一候補になります。本講座は完全 CPU 前提なので、まず ORB で軽く試し、精度が足りなければ SIFT に切り替える、という進め方が現実的です。

| 観点 | SIFT | ORB |
| --- | --- | --- |
| 記述子 | 128次元 `float32` | 32バイト（256ビット）`uint8` |
| 距離 | `NORM_L2`（ユークリッド） | `NORM_HAMMING`（ビット差） |
| 速度（CPU） | 中（重め） | 速い |
| 頑健性 | 高い（視点・回転に強い） | 良好（点数で補う） |
| 向く用途 | 高精度な位置合わせ・合成 | リアルタイム・追跡・組み込み |

この表は「どちらが上」ではなく「どこに効くか」の地図です。両者とも本体に同梱され、追加依存なしで使えます（SIFT は特許失効済み）。実務では「ORB で十分なら ORB、精度が要れば SIFT」という素朴な判断で大きく外しません。次回の第6回では、ここで得た良マッチと `findHomography` を使って、2 枚を実際に貼り合わせるパノラマ合成へ進みます。

## 12. よくあるエラーと対処（チェックリスト）

最後に、この章でつまずきやすい点を「症状 → 原因 → 対処」でまとめます。実装中に詰まったら、まずここを見てください。多くの不具合はこの数個の原因に集約されます。

| 症状 | ほぼ確実な原因 | 対処 |
| --- | --- | --- |
| `ValueError: not enough values to unpack` | `knnMatch` が長さ1のペアを返した | 比率テストで `len(pair) < 2` を先に確認してスキップ |
| マッチがほぼ全部おかしい | ORB に `NORM_L2` 等、記述子と距離の不一致 | SIFT→`NORM_L2`、ORB→`NORM_HAMMING` に揃える |
| `findHomography` が `None`/落ちる | 良マッチが4組未満 | 比率テストを少し緩める／本数を確認してから呼ぶ |
| `cv2.xfeatures2d` が無いと言われる | 古い SIFT の呼び方 | `cv2.SIFT_create()` を使う（特許失効で本体に同梱） |
| FLANN が ORB でエラー/結果が変 | 2進記述子に KD-Tree を指定 | ORB は `algorithm=6`（LSH）。SIFT は `algorithm=1`（KDTree） |
| `matchTemplate` で位置がずれる | 手法の最大/最小の取り違え | CCOEFF/CCORR は `maxLoc`、SQDIFF は `minLoc` |
| 回転・拡大した対象が当たらない | テンプレートは回転・スケール不変でない | マルチスケール探索、または特徴点マッチングへ |
| `HoughCircles` が何も返さない | エッジ画像を渡した／`param2` が高過ぎ | グレー画像を渡す。`param2` を下げて調整 |
| `drawMatches` で色が変 | matplotlib に BGR のまま渡した | `cv2.cvtColor(..., COLOR_BGR2RGB)` してから表示 |

この表の項目が、第5回でつまずく原因のほぼ全てです。逆に言えば、これらを自分で説明でき・回避コードを書けるようになれば、この章のゴールに到達しています。

## 13. まとめ

この章では、素朴なテンプレートマッチングの限界から出発し、局所特徴量（SIFT/ORB）でキーポイントと記述子を抽出し、`knnMatch`＋Lowe の比率テスト（0.75）で曖昧な対応を、RANSAC で幾何的な外れ値を落とす 2 段構えのマッチングを学びました。良マッチ数とインライア率という 2 指標で品質を定量化し、比率しきい値スイープで 0.75 の妥当性を自分の目で確かめました。さらに Hough 変換のパラメータ過敏性を実験し、古典手法それぞれの「効く場面」を地図として持ち帰りました。

ここで得た「良マッチ＋ `findHomography`」は、次回の第6回（ホモグラフィ推定とパノラマ合成）でそのまま 2 枚の画像を貼り合わせる中核部品になります。特徴点マッチングは、パノラマ・物体位置合わせ・キャリブレーション・追跡など、古典 CV の応用が広く枝分かれする結節点です。まずは演習を自力で全問 PASS させ、検出→マッチ→比率テスト→RANSAC という一連の流れを手に馴染ませてから次へ進んでください。

## 🛠 章末ミニプロジェクト — 散らかったシーンからの平面物体検出

ここまでの部品（特徴抽出・比率テスト・RANSAC・四隅投影）を **1 本のパイプライン**に統合する総合課題です。`mini_project.py` を実行すると、次の流れが一気に走ります。

1. **課題生成**: 特徴に富んだ「物体画像（object）」を、既知のホモグラフィ `H_place` で**回転＋遠近変形**し、妨害物（ランダム図形）だらけの背景に貼り込んで「散らかったシーン（scene）」を作る。貼り込んだ 4 隅の真値を保持しておく（評価の物差し）。
2. **検出**: ORB と SIFT の両方で `object → scene` をマッチングし、`knnMatch` ＋ 比率テスト（0.75）で良マッチを選び、`findHomography(RANSAC)` で変換 `H` を推定する。
3. **投影**: `object` の 4 隅を `cv2.perspectiveTransform` で `scene` 座標へ飛ばし、検出枠（多角形）を描く。
4. **評価**: 投影 4 隅と真の 4 隅の**平均コーナー誤差（px）**と**インライア率**を算出して数値で良し悪しを判断する。
5. **対比**: 素朴な**テンプレートマッチング**を同じ scene に当て、回転＋遠近の物体には**スコアが伸びず破綻**することを確認する（＝局所特徴量が必要な理由がここで閉じる）。

この課題は「平面物体を散らかった画像から頑健に見つける」という、看板・書影・商品パッケージ検出や AR マーカ認識の最小核です。`object` を実物の画像に、`scene` をカメラ画像に差し替えれば、そのまま実運用のひな形になります。

**到達の目安**: ORB・SIFT のいずれもコーナー誤差が概ね数 px 以内に収まり、インライア率が高い一方で、テンプレートマッチングのベストスコアは低く張り付くこと。出力は `outputs/05_classical_features_matching/` に以下が保存されます。

| 生成物 | 内容 |
| --- | --- |
| `mini_project_object.png` / `mini_project_scene.png` | 探す物体と、それを貼り込んだ散らかったシーン |
| `mini_project_detect_orb.png` / `mini_project_detect_sift.png` | 各検出器の投影枠（白線が真の四隅、色線が推定四隅） |
| `mini_project_summary.png` | 物体・シーン・ORB/SIFT 検出結果を 1 枚に並べたまとめ図 |
| `mini_project_metrics.json` | 検出点数・良マッチ数・インライア率・コーナー誤差・テンプレ法スコアの数値ログ |

```bash

```

## ❓ よくある落とし穴・FAQ・デバッグ

実装中に詰まったら、まずここを見てください。多くの不具合はこの数個の原因に集約されます（第12節の症状別チェックリストと併せて参照）。

- **Q. `ValueError: not enough values to unpack (expected 2, got 1)` が出る。** A. `knnMatch` が近傍 1 個のとき**長さ 1 のペア**を返すためです。比率テストでは `m, n = pair` の前に必ず `if len(pair) < 2: continue` を入れます。本章の `ratio_test` はこの定石を踏襲しています。
- **Q. マッチがほぼ全部おかしい／インライア率が極端に低い。** A. **記述子の型と距離種別の不一致**が筆頭原因です。SIFT は `NORM_L2`、ORB は `NORM_HAMMING`。ORB に `NORM_L2` を渡すと 2 進列を実数距離で測ってしまい無意味になります。
- **Q. `findHomography` が `None` を返す／落ちる。** A. **良マッチが 4 組未満**です。`len(good) >= 4` を確認してから呼び、足りなければ比率しきい値を少し緩める（0.75→0.8）か、`nfeatures` を増やします。
- **Q. `cv2.xfeatures2d` が無いと言われる。** A. 古い SIFT の呼び方です。特許失効で本体に同梱されたので `cv2.SIFT_create()` を使います（headless 版でも contrib なしで動く）。
- **Q. FLANN が ORB でエラー／結果が壊れる。** A. 2 進記述子に KD-Tree を指定しているからです。ORB は `algorithm=6`（LSH）、SIFT は `algorithm=1`（KDTree）。型に合った index を選びます。
- **Q. 比率テストと crossCheck を併用したら挙動がおかしい。** A. **両者は併用しません**。`crossCheck=True` は内部で k=1 を前提とし `knnMatch(k=2)` と相性が悪いです。どちらか一方の戦略を選びます（一般には比率テストが調整しやすい）。
- **Q. `matchTemplate` の検出位置が毎回ずれる。** A. **手法の最大/最小の取り違え**です。`TM_CCOEFF_NORMED`/`TM_CCORR_NORMED` は `max_loc`、`TM_SQDIFF`/`TM_SQDIFF_NORMED` は `min_loc` が答えです。
- **Q. `HoughCircles` が何も返さない／幻の円が大量に出る。** A. 入力に**エッジ画像を渡している**（円はグレー画像を渡す）か、`param2` が高過ぎ／低過ぎです。`param2` を下げると検出が緩くなり、上げると厳しくなります。
- **Q. matplotlib に渡したら色が反転した。** A. cv2 は **BGR**、matplotlib は RGB です。`cv2.cvtColor(img, cv2.COLOR_BGR2RGB)` を挟んでから `imshow` します。headless では `matplotlib.use("Agg")` を `pyplot` import 前に呼び、`savefig` で保存します。
- **Q. 結果が実行のたびに変わって再現しない。** A. 合成画像の乱数 `seed` を固定し、ORB の `nfeatures` を明示します。RANSAC はわずかにぶれますが、インライア率の桁が変わるほどではありません。

## 🚀 発展トピック・参考

- **AKAZE / BRISK / KAZE**: ORB と SIFT の中間にあたる特徴量。`cv2.AKAZE_create()` などで作れ、2 進記述子なら `NORM_HAMMING` を使います。回転・スケール頑健性と速度のバランスが ORB と少し違うので、同じパイプラインで差し替え比較すると学びが深いです。
- **`goodFeaturesToTrack`（Shi-Tomasi）と Harris コーナー**: 記述子を持たない「コーナー検出だけ」の古典。追跡（Lucas-Kanade オプティカルフロー）の起点として後の回で再登場します。
- **比率テストの自動調整**: 難しい視点ペアでは 0.75 固定より、良マッチ数が一定本数（例: 30 本）を超える最小しきい値を二分探索する、といった適応戦略もあります。
- **`cv2.Stitcher` と高レベル API**: 本章の「良マッチ＋ `findHomography`」を内部で行う完成品。次回の第6回でパノラマ合成として手組みパイプラインと比較します。
- **RANSAC の代替**: `cv2.findHomography` には `cv2.RANSAC` の他に `cv2.LMEDS`・`cv2.RHO` が選べます。外れ値割合が高い／低いで向き不向きがあるので、`ransacReprojThreshold` と併せて挙動を観察すると理解が進みます。
- **スケール不変テンプレートマッチング**: マルチスケール探索は本章で扱いましたが、回転まで含めるとコストが爆発します。これが「だから回転・スケール不変な局所特徴量が要る」という設計判断の出発点です。
- 参考ドキュメント: OpenCV 公式チュートリアル「Feature Detection and Description」 https://docs.opencv.org/4.x/db/d27/tutorial_py_table_of_contents_feature2d.html ／ Lowe, D. (2004) "Distinctive Image Features from Scale-Invariant Keypoints"（比率テストの原典）。
